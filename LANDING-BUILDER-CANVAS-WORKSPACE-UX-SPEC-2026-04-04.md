# Продуктовый UX spec: canvas workspace Нордик

## Зачем этот документ

Этот документ фиксирует не внутренний JSON contract, а взрослую рабочую оболочку canvas editor.

Причина появления документа:

1. текущий canvas уже функционален, но визуально еще похож на служебный backend-экран;
2. пользователю нужен широкий рабочий холст для desktop-режима;
3. sidebar-панели не должны отъедать полезную ширину canvas;
4. device switching, навигация по странице и работа с настройками должны ощущаться как продуктовый editor workspace, а не как набор bootstrap-карточек.

## 1. Главный принцип workspace

Canvas должен выглядеть как редактор страницы, а не как страница настроек компонента.

На desktop главным элементом экрана должен быть не левый или правый sidebar, а сама страница.

Поэтому базовый принцип такой:

1. canvas всегда занимает максимальную доступную ширину рабочего окна;
2. боковые панели существуют поверх canvas как drawers;
3. по умолчанию на desktop обе панели открыты;
4. при необходимости они прячутся за край окна, но оставляют видимую ручку возврата;
5. canvas не должен ломаться при открытии и закрытии панелей.

## 1.1. Язык интерфейса для новичков

Workspace должен быть понятен человеку без технической подготовки.

Обязательные правила языка:

1. все пользовательские подписи, подсказки и кнопки только на русском;
2. англоязычные слова и сокращения в пользовательских экранах не использовать;
3. технические названия (`slot`, `layout`, `token`, `adapter`, `contract`) не показывать как основной язык экрана;
4. если термин неизбежен, рядом обязательно давать простое русское пояснение;
5. формулировки должны быть короткими и практичными: что делает действие и какой будет результат.

## 2. Каноническая композиция экрана

У workspace должно быть 5 уровней:

1. верхняя sticky-панель редактора;
2. слой левой библиотеки;
3. центральный viewport canvas;
4. слой правого инспектора;
5. нижний служебный feedback layer для autosave/status/toast.

Схема:

`Top bar -> Left drawer + Canvas viewport + Right drawer -> Status layer`

## 3. Верхняя панель редактора

### 3.1. Что должно быть слева

1. кнопка `Назад к страницам`;
2. название страницы;
3. статус страницы;
4. компактный индикатор последнего сохранения.

### 3.2. Что должно быть в центре

1. device switcher: `Компьютер`, `Планшет`, `Телефон`;
2. control `Подогнать`;
3. control масштаба, если понадобится второй фазой.

### 3.3. Что должно быть справа

1. `Сохранить`;
2. `Предпросмотр`;
3. `Тема страницы`;
4. `Опубликовать` или будущий publish-action;
5. кнопки открытия левого и правого drawer.

### 3.4. Что нельзя выводить в top bar

1. служебные route keys;
2. shell slot ids;
3. bootstrap breakpoint names;
4. raw database semantics.

## 4. Левый drawer: библиотека и навигация

Левый sidebar должен стать не просто списком вставки, а навигационно-библиотечным drawer.

Его структура:

1. вкладка `Добавить`;
2. вкладка `Структура`;
3. вкладка `Шаблоны`;
4. вкладка `Виджеты`.

### 4.1. Состояние по умолчанию

На desktop drawer открыт по умолчанию.

Ширина:

1. базово 320px;
2. в расширенном состоянии до 360px;
3. при скрытии уезжает за левый край окна, но оставляет ручку 40-48px.

### 4.2. Поведение

1. drawer живет поверх canvas, а не в документном потоке;
2. закрытие drawer не должно пересобирать холст;
3. состояние drawer должно запоминаться отдельно для desktop и mobile;
4. при ширине экрана ниже desktop drawer должен превращаться в off-canvas panel на весь экран по высоте.

### 4.3. Вкладка `Структура`

Это обязательное дополнение к текущему UX.

Она должна показывать:

1. список секций страницы сверху вниз;
2. активную секцию;
3. быстрый jump к секции;
4. reorder секций без необходимости тянуть длинный экран;
5. быстрые действия: дублировать, скрыть, удалить.

Это закрывает проблему навигации по длинной странице.

## 5. Центральный viewport canvas

### 5.1. Роль viewport

Canvas не должен просто растягиваться на 100% ширины браузера как белая карточка.

Нужен именно viewport редактора:

1. отдельный фон workspace;
2. центрированная плоскость страницы;
3. управляемая ширина preview по устройству;
4. независимость от ширины открытых drawer-панелей.

### 5.2. Desktop-ширина workspace

Для desktop редактора нужно считать каноничным широкий рабочий режим.

Целевые размеры:

1. максимальная ширина workspace shell: 100%;
2. внутренний padding editor shell: 20-24px;
3. максимальная полезная ширина viewport на desktop: 1600-1760px;
4. page preview внутри viewport: по device preset, а не по ширине карточки bootstrap.

### 5.2.1. Композиционная сетка canvas

Для взрослого режима workspace фиксируем:

1. базовая рабочая сетка страницы: 12 колонок;
2. основной режим ширины: full width;
3. плотный ритм отступов как стартовый профиль;
4. готовые журнальные раскладки должны быть доступны как быстрые пресеты;
5. скругления по умолчанию выключены и включаются только осознанно через настройки внешнего вида.

### 5.3. Device widths

Для первой продуктовой версии зафиксировать такие viewport widths:

1. `Компьютер`: 1440px preview width;
2. `Планшет`: 834px preview width;
3. `Телефон`: 390px preview width.

Дополнительно:

1. `Подогнать` должен уменьшать preview scale, если экран меньше целевой ширины;
2. сам device width не должен зависеть от того, открыт ли sidebar;
3. на больших мониторах должно оставаться ощущение просторного editor workspace.

### 5.4. Визуальный язык canvas

Canvas должен уходить от схемы `карточка внутри карточки внутри карточки`.

Нужен более page-like подход:

1. у workspace отдельный мягкий фон;
2. у page preview отдельная плоскость с тенью и radius;
3. section selection и hover более тонкие и продуктовые;
4. служебные кнопки секции живут в overlay-toolbar, а не ломают её компоновку;
5. column dropzones и reorder affordances видны только при hover/selection.

## 6. Правый drawer: инспектор

### 6.1. Роль

Правая панель должна стать полноценным properties drawer, а не просто третьей bootstrap-card колонкой.

### 6.2. Состояние по умолчанию

1. на desktop открыта по умолчанию;
2. ширина 360-400px;
3. может быть свернута за правый край окна с оставлением ручки;
4. состояние тоже запоминается отдельно для desktop и mobile.

### 6.3. Внутренняя структура

Внутри инспектора нужен не бесконечный список полей, а режимы:

1. `Страница`;
2. `Секция`;
3. `Колонка`;
4. `Элемент`;
5. `Виджет`.

Для каждого режима:

1. сверху entity header;
2. ниже группы настроек;
3. редко используемые поля в `Дополнительно`;
4. destructive actions в sticky footer панели.

### 6.4. Чего не должно быть

1. сырого нагромождения служебных полей без группировки;
2. постоянного показа служебных CSS-полей на первом экране;
3. ощущения, что это форма настроек из CMS, а не редактор страницы.

## 7. Навигация по canvas

Это отдельный обязательный слой, которого сейчас почти нет.

Нужно обеспечить три сценария:

1. быстрая навигация к секции;
2. понятный возврат из editor в список страниц;
3. явный переход из page-level mode в section-level mode и обратно.

### 7.1. Что добавить

1. breadcrump `Страницы / {Название страницы}`;
2. выделяемый page mode chip;
3. кнопка `К странице` в структуре;
4. jump navigation по секциям;
5. sticky mini-map или outline на следующей фазе.

## 8. Переключение устройств

### 8.1. Что не устраивает в базовой версии

Сейчас device toggle воспринимается как обычный backend control.

Продуктовый режим должен ощущаться как переключение viewport preview.

### 8.2. Каноническое поведение

1. toggle визуально находится в центре top bar;
2. активное устройство должно менять не только кнопку, но и реальную ширину preview;
3. рядом должен быть понятный label текущего viewport width;
4. при переключении canvas остается на одном visual center;
5. скрытые на устройстве элементы не исчезают бесследно, а получают понятное muted-состояние или badge.

### 8.3. Mobile UX самого editor workspace

На узких экранах editor workspace переходит в mobile-shell:

1. canvas занимает всё пространство;
2. левый drawer открывается модально;
3. правый drawer открывается модально;
4. device switcher остается доступным из top bar;
5. page actions уходят в compact menu.

## 9. Что взять из nordic-builder.ru как verified reference

По текущему референсу полезно зафиксировать такие паттерны:

1. на desktop панель свойств открыта по умолчанию;
2. состояние панели должно запоминаться отдельно для desktop и mobile;
3. editor shell должен мыслиться как приложение, а не как страница настроек;
4. properties panel и canvas должны быть независимыми по layout-состоянию.

## 10. Фазы внедрения

### Фаза 1. Workspace shell refactor

Без ломки data model:

1. перестроить canvas page layout в sticky top bar + overlay drawers + viewport;
2. сделать canvas шире для desktop;
3. вынести библиотеку и инспектор в drawers;
4. добавить desktop/mobile persisted state для drawer-панелей.

### Фаза 2. Device viewport refactor

1. ввести канонические viewport widths;
2. добавить `Подогнать`;
3. центрировать preview;
4. развести workspace width и page preview width.

### Фаза 3. Navigation and structure

1. добавить вкладку `Структура`;
2. добавить быстрые jump actions к секциям;
3. добавить более явную page/section navigation.

### Фаза 4. Visual canvas polish

1. убрать лишнюю карточность;
2. сделать overlay toolbars для секций и node;
3. перевести canvas в более page-like visual style;
4. сделать drag/drop affordances аккуратнее.

## 11. Критерии качества взрослого canvas

Canvas можно считать продуктово зрелым только если одновременно соблюдено всё ниже:

1. на desktop главным визуальным объектом остается страница, а не сайдбары;
2. библиотека и инспектор не съедают полезную ширину canvas;
3. device switching ощущается как смена viewport, а не как backend toggle;
4. длинной страницей можно управлять без хаотичного скролла;
5. editor shell выглядит как отдельный продуктовый workspace;
6. новичок понимает, где он добавляет, где настраивает и где переключает устройство.

## 12. Ближайшее решение для текущего репозитория

Следующим практическим шагом считать не мелкую правку отдельных карточек, а именно refactor canvas shell.

Приоритет:

1. wide desktop canvas;
2. overlay drawers;
3. top bar navigation;
4. viewport-based device switching;
5. только потом локальная косметика секций.
