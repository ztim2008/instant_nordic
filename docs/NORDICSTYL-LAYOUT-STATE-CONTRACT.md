# NordicStyl Layout State Contract

## Зачем нужен этот контракт

Builder уже умеет показывать реальную схему шаблона и работать как редакционный слой поверх `modern` / `nordics`.

Следующий обязательный шаг: сделать layout адаптивным не только по CSS, но и по самой структуре.

Нам нужен короткий и устойчивый контракт, чтобы:

- у каждого breakpoint был свой layout state
- сохранялось наследование `desktop -> tablet -> mobile`
- пользователь переопределял только нужные отличия
- внутренняя математика не разваливалась при full width, sidebars и drag-resize

## Базовые правила

### Breakpoints

В UI и в продуктовой логике используем три режима:

- `desktop`
- `tablet`
- `mobile`

### Наследование

Порядок наследования всегда один:

- `desktop` -> `tablet` -> `mobile`

Смысл:

- `desktop` хранит базовую схему страницы
- `tablet` хранит только отличия от `desktop`
- `mobile` хранит только отличия от уже собранного `tablet`

### Что пользователь должен чувствовать

Пользователь не редактирует три несвязанные страницы.

Пользователь редактирует одну страницу в трех режимах:

- на `desktop` задает основную структуру
- на `tablet` подправляет только то, что должно отличаться
- на `mobile` доводит стек, порядок и ширины до финального мобильного вида

## Что такое layout state

Layout state отвечает только за структуру и компоновку.

Он не отвечает за:

- цвета
- типографику
- фон
- декоративные стили

Это важно: layout и style должны быть разными слоями.

### В layout state входят

- набор рядов
- порядок рядов
- видимость ряда
- режим ширины ряда: `grid` или `full`
- набор колонок внутри ряда
- порядок колонок
- ширины колонок в `12` unit-сетке
- видимость колонок
- режим стека колонок на breakpoint
- список виджетов и секций внутри колонок
- порядок виджетов
- скрытие отдельных узлов на breakpoint

## Главный принцип сетки

### 12 колонок оставляем

Внутри layout engine оставляем сетку `12` units.

Это нужно для:

- drag-resize без хаоса
- предсказуемого сохранения ширин
- нормального наследования между breakpoint-ами
- совместимости с текущей Bootstrap-основой InstantCMS

### 100% ширина тоже поддерживается

`100%` не заменяет `12` колонок.

`100%` это отдельный режим внешней рамки ряда:

- `width_mode = grid`
- `width_mode = full`

Смысл:

- `grid` = ряд живет внутри обычной контейнерной ширины
- `full` = ряд может тянуться на всю доступную ширину

Но даже в `full` режиме внутренняя компоновка колонок все равно считается через `12` units.

Именно так шаблон сможет быть и `100%`, и управляемым.

## Минимальная модель данных

### Продуктовый вид

Человечески layout state выглядит так:

```yaml
layout_state:
  desktop:
    rows: [...]
  tablet:
    overrides: {...}
  mobile:
    overrides: {...}
```

### Практическое правило хранения

Для реализации берем такой принцип:

- `desktop` хранится как полный snapshot
- `tablet` хранится как набор overrides к `desktop`
- `mobile` хранится как набор overrides к уже собранному `tablet`

Это проще и безопаснее, чем хранить три полных независимых дерева.

## Узлы и стабильные идентификаторы

Каждый узел layout должен иметь стабильный `uid`.

Минимальные типы узлов:

- `row`
- `column`
- `widget`
- `section`

Зачем это нужно:

- чтобы override применялся к тому же узлу на другом breakpoint
- чтобы drag-resize и reorder не ломали связь между режимами
- чтобы inspector и builder смотрели на одну и ту же сущность

## Что можно переопределять на breakpoint

Минимальный список override-полей:

- `visible`
- `order`
- `width_units`
- `width_mode`
- `stack_mode`
- `children_order`

### Рекомендуемые значения

`visible`

- `true`
- `false`

`width_mode`

- `grid`
- `full`

`stack_mode`

- `inherit`
- `auto`
- `stack`
- `grid`

Смысл:

- `inherit` берет поведение у предыдущего breakpoint
- `auto` позволяет системе самой стекать колонки по правилам breakpoint-а
- `stack` принудительно собирает колонки вертикально
- `grid` оставляет колонки в ряд, если это еще допустимо

## Правила сборки breakpoint state

### Desktop

`desktop` это базовая схема.

Если пользователь ничего не переопределял, именно она и есть source of truth.

### Tablet

Tablet state собирается так:

1. берется `desktop`
2. применяются `tablet.overrides`

### Mobile

Mobile state собирается так:

1. берется уже собранный `tablet`
2. применяются `mobile.overrides`

## Правила поведения по умолчанию

Чтобы UI не был тяжелым, системе нужны безопасные дефолты.

### Если у breakpoint нет overrides

Он полностью наследует предыдущий режим.

### Если на mobile нет явного layout override

Система может автоматически:

- стекать колонки в `12/12`
- сохранять порядок колонок
- не ломать widget bindings

### Если ряд переведен в `full`

Это не должно автоматически убирать sidebars или ломать body layout.

`full` влияет только на ширину ряда, а не на существование соседних зон.

## Короткий MVP-контракт для реализации

На первом рабочем шаге достаточно вот этого:

1. Ввести layout state с `desktop`, `tablet`, `mobile`.
2. Хранить `desktop` как полный snapshot.
3. Хранить `tablet/mobile` как overrides.
4. Для ряда поддержать `width_mode: grid|full`.
5. Для колонки поддержать `width_units` и `visible`.
6. Для mobile включить авто-стек колонок, если override не задан.
7. Не смешивать layout state со style state.

## Пример в человеческом виде

```yaml
layout_state:
  desktop:
    rows:
      - uid: row-content
        width_mode: grid
        columns:
          - uid: col-main
            width_units: 8
          - uid: col-side
            width_units: 4

  tablet:
    overrides:
      row-content:
        columns:
          col-main:
            width_units: 7
          col-side:
            width_units: 5

  mobile:
    overrides:
      row-content:
        stack_mode: stack
        columns:
          col-main:
            width_units: 12
          col-side:
            width_units: 12
```

## Как это стыкуется с текущим NordicStyl

У `nordicstyl` уже есть device-aware модель для style-layer.

Практический вывод:

- UI builder-а должен мыслить `desktop / tablet / mobile`
- layout layer может жить в этих же названиях
- если для совместимости понадобится внутренний adapter, `desktop` можно маппить в текущую базовую device-ветку без изменения продуктового UX

Главное правило:

- пользователь работает в терминах `desktop / tablet / mobile`
- внутренняя совместимость не должна выплывать в UI

## Что делать следующим шагом

После фиксации этого контракта следующий технический шаг такой:

1. Добавить в builder device switcher: `desktop / tablet / mobile`.
2. В state builder-а ввести `layout_state` вместо одного плоского дерева rows.
3. Сделать resolver: `desktop -> tablet -> mobile`.
4. Добавить для row переключатель `grid / full`.
5. Добавить первые column overrides для tablet/mobile.

Этого уже хватит, чтобы идти в реализацию без смены базовой архитектуры позже.
