# NordicStyl — план разработки (по‑взрослому)

## Суть

Собираем гибридный продукт:

- дочерний шаблон `templates/nordics` (наследник `modern`, минимум оверрайдов)
- компонент `nordicstyl` уже начат и сейчас даёт style-layer: hook → `/css` → admin CRUD правил
- текущий picker и карта селекторов остаются как вспомогательный слой для live-стилизации
- главный продуктовый маршрут: фронтовой builder по ссылке вида `/builder`, а не отдельные backend-формы
- во фронтовом builder пользователь сразу видит стандартную сетку дочернего шаблона, а не пустой холст
- стартовую логику рядов, колонок, позиций и привязок виджетов берём из текущей layout-схемы `modern`/дочернего шаблона, а не выдумываем заново
- в canvas пользователь собирает ряды, секции, системные виджеты и библиотечные виджеты через плюсик
- ширина рядов/колонок регулируется drag-and-drop, без ручных bootstrap-расчётов со стороны пользователя
- live-инспектор поверх canvas строится на базе уже начатого `nordicstyl`, а не как отдельная новая сущность с нуля
- style-layer должен уметь менять внешний вид любого элемента сайта прямо на странице, без ручного CSS и без похода по backend-формам как по основному UX
- стиль должен учитывать состояния элемента и далее режимы устройств: desktop/mobile как отдельные визуальные варианты
- после сохранения изменения собираются в чистый CSS и подключаются поверх шаблона как дополнительный слой, без жёсткой привязки к конкретному шаблону
- далее — глобальная “система шаблонов” и виджеты/секции (как OneBuilder) для сборки лендингов

Цель MVP: **перестать править Modern руками и перестать собирать страницу с нуля**. Пользователь открывает `/builder`, видит стартовую сетку `nordics` и собирает страницу прямо с морды сайта.

## Что уже реально есть в `nordicstyl`

- runtime CSS endpoint `/nordicstyl/css`
- hook `before_print_head` для подключения CSS на сайте
- backend CRUD правил
- picker с iframe/inject и подсветкой элемента
- selector map через `selector-map.json`

Вывод: `nordicstyl` не выбрасываем. Его нужно **расширять в сторону builder-а**, но не оставлять финальный продукт CSS-центричным.

## Что берём из идеи живого style-layer

- пользователь выбирает любой элемент или группу сходных элементов прямо на странице сайта
- внешний вид меняется мышкой в компактном on-site интерфейсе, без ручного написания CSS
- правим не только базовые цвета и шрифты, но и фон, spacing, рамки, размеры, положение и другие визуальные параметры
- для одного и того же элемента должны поддерживаться состояния: обычное, hover и другие нужные режимы
- для следующего уровня inspector-а закладываем device-aware режимы: отдельный вид для desktop/mobile
- сохранённые изменения должны компилироваться в чистый CSS, который просто подключается к шаблону как дополнительный stylesheet

Вывод:
- это не отдельный “редактор в админке”, а живой инспектор на самом сайте
- нейминг донора не переносим в код, UI, маршруты и продуктовые сущности

## Что берём из шаблонной логики `modern`

- текущую схему рядов/колонок/позиций из layout child шаблона
- существующие привязки системных виджетов к позициям
- контейнерную и bootstrap-совместимую механику как внутреннюю основу

Что НЕ делаем:

- не придумываем с нуля отдельную сетку, если её уже можно унаследовать из `modern`
- не заставляем пользователя думать в терминах `col-*` и position names, даже если внутри они сохраняются

## План (этапы + критерии готовности)

### 0) Нейминг и бренд (обязательное правило)
- 🟢 В разработке и документации НЕ используем чужие названия/слова (названия донорских компонентов/пакетов)
- 🟢 Внешние артефакты называем нейтрально: “selector map”, “карта селекторов”, `selector-map.json`

DoD:
- в roadmap/UX/сообщениях пользователю нет чужих названий

### 1) Основа и безопасность
- 🟢 Checkpoint/rollback flow (DB dump + git snapshot)
- 🟢 Документация и ежедневные статусы (`docs/status`)

DoD:
- перед рискованными изменениями всегда есть snapshot/tag и дамп
- есть короткий daily статус без “простыней”

### 2) Компонент NordicStyl (core)
- 🟢 DB модель правил
- 🟢 Runtime: hook + `/nordicstyl/css`
- 🟢 Backend: CRUD правил + CSRF
- 🟢 Инсталлер: миграции + трекинг `{#}nordicstyl_migrations`

DoD:
- можно создать правило в админке и увидеть эффект на сайте
- повторная установка/обновление не ломает данные

### 3) Picker MVP (iframe inject)
- 🔵 Inject-режим (iframe) с подсветкой элемента
- 🟢 Клик по элементу → селектор (минимально полезный)
- 🟢 Передача селектора в форму правила (автозаполнение)

DoD:
- сценарий «открыть страницу → кликнуть элемент → получить селектор → сохранить правило → увидеть изменения» работает

### 4) Импорт карты селекторов
- 🔵 Импорт `selector-map.json` (как “словарь элементов”)
- 🔵 UI выбора элемента из списка → подстановка селектора

DoD:
- без кликов по странице можно быстро выбирать типовые элементы (header, buttons, cards…)

### 5) Front Canvas Builder (главный экран продукта)
- 🟡 Фронтовый маршрут builder-а: `/builder` или близкий продуктовый URL
- 🟡 При открытии показываем не пустой экран, а стартовую сетку/каркас `nordics`, собранную из текущей схемы дочернего шаблона
- 🟡 Canvas 1:1 по логике сборки схем: ряды, секции, колонки, зоны
- 🟡 Adaptive layout state: `desktop / tablet / mobile` с наследованием и override-логикой
- 🟡 Добавление через плюсик: ряд, секция, системный виджет, библиотечный виджет
- 🟡 Ширина колонок/зон меняется мышкой через drag handles; система сама пересчитывает сетку внутри
- 🟡 Ряд может жить в режиме `grid` или `full`, не теряя внутреннюю 12-unit математику
- 🟡 Библиотека виджетов с категориями, поиском и превью
- 🟡 Текущие position/widget bindings из шаблона сохраняются как внутренняя основа, но во frontend UI показываются человеческими названиями
- 🟡 Сначала builder управляет только телом страницы; header/footer/shell пока живут в шаблоне
- 🟡 Save/load/publish loop для структуры страницы без ручного JSON

DoD:
- пользователь открывает builder и сразу понимает, с чего начать
- страницу можно собрать из рядов/секций/виджетов без пустого старта
- пользователь меняет ширину колонок визуально, не думая про Bootstrap-классы и проценты
- результат сохраняется и одинаково выглядит в builder и на live

### 6) Live Inspector и style-layer на базе `nordicstyl`
- 🟡 Отдельный live-инспектор поверх canvas, а не backend-форма
- 🟡 Переиспользование уже сделанного: CSS runtime, picker, selector map, правила, токены
- 🟡 Редактирование выбранного узла canvas “на месте”: стиль, spacing, фон, состояния, custom CSS где нужно
- 🟡 Поддержка состояний элемента: обычное, hover, далее другие нужные состояния без ручного CSS со стороны пользователя
- 🟡 Поддержка device-aware режимов: как минимум desktop/mobile для разных визуальных состояний одного и того же узла
- 🟡 После сохранения стиль собирается в чистый CSS и подключается поверх активного шаблона как дополнительный слой
- 🟡 Click-to-pick и selector map остаются как вспомогательные инструменты, а не как главный продуктовый сценарий
- 🟡 Live preview без расхождения preview/live

Порядок работ:
- расширенный visual style-layer делаем после стабилизации этапов 2 и 3, потому что runtime правил и picker уже являются его фундаментом

DoD:
- стиль выбранного узла можно менять прямо в builder
- состояния и device-режимы применяются без ручной правки CSS
- сохранённые правки живут как чистый CSS-слой и не зависят от конкретной вёрстки редактора
- текущий `nordicstyl` не дублирует builder, а усиливает его как design-инспектор

### 7) Условия применимости (по страницам)
- 🟡 Минимальная фильтрация применения правил по `uri` (scope + masks)

DoD:
- одно и то же правило можно включить только для нужных страниц (без усложнения)

### 8) Шаблон `nordics` как тонкий слой
- 🟡 Зафиксировать “точки оверрайда” (что меняем в `nordics`, что не трогаем)
- 🟡 Минимальные override-файлы (не копировать Modern целиком)
- 🟡 Точка расширения карты селекторов: `templates/nordics/selector-map.json` (и аналогично для активного шаблона)

Дополнение:
- `nordics` даёт стартовую сетку/каркас, который пользователь видит сразу при входе в builder
- `nordics` остаётся технически совместимым с Bootstrap/InstantCMS, но в UI builder-а пользователь не работает bootstrap-терминами
- базовый source-of-truth для стартового canvas: унаследованная схема `modern` + её привязки позиций и виджетов

DoD:
- обновления Modern не требуют ручного мержа десятков файлов

### 9) Блоки/секции и виджеты (как OneBuilder)
- 🟡 3–5 продающих секций (hero/benefits/cta/faq/contacts)
- 🟡 Единые токены/стили и совместимость с `nordics`
- 🟡 Адаптеры для системных виджетов InstantCMS, чтобы их можно было ставить из canvas

DoD:
- “сайт за вечер” из готовых секций без ручной верстки

## Первый взрослый MVP (с чего реально стартуем)

1. Фронтовый маршрут `/builder` с редакционным режимом.
2. Стартовая сетка `nordics`, собранная из текущей схемы `modern`, видимая сразу после входа.
3. Добавление ряда/секции/виджета через плюсик.
4. Drag-and-drop изменение ширины колонок.
5. Live-инспектор на базе `nordicstyl` для выбранного узла.
6. Сохранение и повторная загрузка структуры страницы.

Жёсткое правило MVP:
- пользователь не должен видеть и настраивать `col-*`, проценты ширины или bootstrap-расчёты вручную

### 10) Глобальная система шаблонов
- 🟡 Единый способ выбирать/переключать шаблон/пресет для сайта и (минимально) для отдельных страниц
- 🟡 Совместимость с обновлениями Modern + отсутствие ручного мержа

DoD:
- можно безопасно переключить внешний вид без правки файлов и без потери данных
