# NordicStyl — план разработки (по‑взрослому)

## Суть

Собираем гибридный продукт:

- дочерний шаблон `templates/nordics` (наследник `modern`, минимум оверрайдов)
- компонент `nordicstyl` уже начат и сейчас даёт style-layer: hook → `/css` → admin CRUD правил
- текущий picker и карта селекторов остаются как вспомогательный слой для live-стилизации
- главный продуктовый маршрут: фронтовой builder по ссылке вида `/builder`, а не отдельные backend-формы
- во фронтовом builder пользователь сразу видит стандартную сетку дочернего шаблона, а не пустой холст
- стартовую логику рядов, колонок, позиций и привязок виджетов берём из текущей layout-схемы `modern`/дочернего шаблона, а не выдумываем заново
- в canvas пользователь собирает ряды, секции, системные виджеты и библиотечные виджеты через плюсик
- ширина рядов/колонок регулируется drag-and-drop, без ручных bootstrap-расчётов со стороны пользователя
- live-инспектор поверх canvas строится на базе уже начатого `nordicstyl`, а не как отдельная новая сущность с нуля
- style-layer должен уметь менять внешний вид любого элемента сайта прямо на странице, без ручного CSS и без похода по backend-формам как по основному UX
- стиль должен учитывать состояния элемента и далее режимы устройств: desktop/mobile как отдельные визуальные варианты
- после сохранения изменения собираются в чистый CSS и подключаются поверх шаблона как дополнительный слой, без жёсткой привязки к конкретному шаблону
- далее — глобальная “система шаблонов” и виджеты/секции (как OneBuilder) для сборки лендингов

Цель MVP: **перестать править Modern руками и перестать собирать страницу с нуля**. Пользователь открывает `/builder`, видит стартовую сетку `nordics` и собирает страницу прямо с морды сайта.

## Что уже реально есть в `nordicstyl`

- runtime CSS endpoint `/nordicstyl/css`
- hook `before_print_head` для подключения CSS на сайте
- backend CRUD правил
- picker с iframe/inject и подсветкой элемента
- selector map через `selector-map.json`

Вывод: `nordicstyl` не выбрасываем. Его нужно **расширять в сторону builder-а**, но не оставлять финальный продукт CSS-центричным.

## Что берём из идеи живого style-layer

- пользователь выбирает любой элемент или группу сходных элементов прямо на странице сайта
- внешний вид меняется мышкой в компактном on-site интерфейсе, без ручного написания CSS
- правим не только базовые цвета и шрифты, но и фон, spacing, рамки, размеры, положение и другие визуальные параметры
- для одного и того же элемента должны поддерживаться состояния: обычное, hover и другие нужные режимы
- для следующего уровня inspector-а закладываем device-aware режимы: отдельный вид для desktop/mobile
- сохранённые изменения должны компилироваться в чистый CSS, который просто подключается к шаблону как дополнительный stylesheet

Вывод:
- это не отдельный “редактор в админке”, а живой инспектор на самом сайте
- нейминг донора не переносим в код, UI, маршруты и продуктовые сущности

## Что берём из шаблонной логики `modern`

- текущую схему рядов/колонок/позиций из layout child шаблона
- существующие привязки системных виджетов к позициям
- контейнерную и bootstrap-совместимую механику как внутреннюю основу

Что НЕ делаем:

- не придумываем с нуля отдельную сетку, если её уже можно унаследовать из `modern`
- не заставляем пользователя думать в терминах `col-*` и position names, даже если внутри они сохраняются

## Взрослый план продолжения (visual-first)

Главная продуктовая цель следующего этапа:

- пользователь должен чувствовать не “редактор рядов и колонок”, а живой визуальный редактор страницы
- builder остается главным экраном продукта, а style-layer `nordicstyl` становится его design-inspector слоем
- `desktop / tablet / mobile` должны выглядеть как три режима просмотра одной и той же страницы, а не как три статичных списка с разной подписью

### Как это должно работать в итоге

Итоговый пользовательский сценарий:

1. Пользователь открывает builder и сразу видит реальную стартовую страницу на основе `nordics` / унаследованной схемы.
2. Кликает по блоку или виджету прямо на canvas.
3. Справа открывается inspector с двумя слоями: `Layout` и `Style`.
4. При переключении `Desktop / Tablet / Mobile` меняется не только label, а сам viewport canvas и визуальная компоновка.
5. Если на новом устройстве нет отдельного override, пользователь видит унаследованное состояние и понятную пометку “используется версия от предыдущего режима”.
6. Первое изменение на `tablet` или `mobile` создает override только для нужного узла, а не копию всей страницы.
7. После сохранения layout и style живут как два согласованных слоя: структура страницы и CSS-слой поверх нее.

### Жесткие продуктовые правила

- не возвращаться к backend-first UX и не уводить основной сценарий в формы вне canvas
- не показывать пользователю bootstrap-термины, `col-*`, проценты и внутренние position names
- не делать отдельный “редактор стилей” как второй продукт рядом с builder
- не делать три независимых layout-дерева для `desktop / tablet / mobile`

### Новый базовый принцип сохранения: admin-first live apply

Продуктовое решение следующего этапа:

- для администратора основной сценарий должен быть: `изменил -> сохранил -> сразу увидел на сайте`
- builder не должен ощущаться как отдельный мир черновиков, который потом еще надо “дотащить” до живого сайта
- история изменений и `reset to default` являются главной страховкой вместо тяжелого draft-first UX

Что это значит практически:

1. Внешне для пользователя кнопка `Сохранить` должна означать применение результата к live-сайту.
2. Если внутри системе нужен технический временный state, он не должен торчать в продуктовый UX как отдельный обязательный шаг.
3. `Publish` как отдельная сущность допустим только как временная техническая стадия текущего stable-state, но не как целевая продуктовая модель.
4. Возврат назад обеспечивается не черновиками, а историей действий, точками отката и `default reset`.

Итоговое правило:

- админ всегда работает с живой страницей
- система должна быть простой в ощущении и безопасной в откате

### Правило responsive-визуализации

Проблема текущего ощущения:

- сейчас device-switcher уже есть, но пользователь может воспринимать режимы как почти статичные состояния
- если visual-first обещание остается главным, canvas должен визуально реагировать на breakpoint

Что считаем правильным UX:

1. Canvas имеет preview-frame для каждого устройства:
	- `desktop` = широкий рабочий режим
	- `tablet` = суженный frame с реальной перестройкой колонок по resolver-логике
	- `mobile` = узкий frame, где по умолчанию работает auto-stack, если override не задан
2. Переключение устройства меняет:
	- ширину preview-frame
	- плотность отступов и поведение handles
	- видимость stack/grid поведения колонок
	- подсказку о том, inherited это состояние или уже свой override
3. На `mobile` пользователь не должен видеть фальшивую “десктопную сетку в узкой коробке”. Если колонка унаследована как stack, canvas обязан показывать стек визуально.
4. Row mode `grid / full` должен быть виден глазами, а не только в select-control inspector-а.
5. Для каждого узла нужен маленький visual badge состояния:
	- `inherited`
	- `override`
	- `hidden on this device`

Практический вывод:

- следующий шаг не в “еще одном списке настроек”, а в том, чтобы сделать canvas device-responsive по визуализации, а inspector — объясняющим, откуда взялось текущее состояние

## Execution plan на следующие итерации

### Этап 0. Live save foundation вместо draft-first UX

Цель:

- перевести продуктовую модель на понятное поведение `сохранил = получил на сайте`

Что делаем:

- определяем новый основной контракт сохранения: builder пишет сразу в live-состояние для админа
- текущий draft-state перестаем считать главным UX-сценарием
- историю изменений делаем как список server-side snapshots / revisions для layout и style
- `reset to default` оставляем как быстрый безопасный возврат к базовой схеме шаблона
- если нужен внутренний технический autosave, он работает как невидимая страховка, а не как отдельная пользовательская сущность

Минимальные safety-правила:

- только авторизованный админ с существующими правами компонента
- обязательные CSRF и серверная валидация payload
- история изменений перед destructive операциями
- быстрый rollback на предыдущую revision без ручной археологии

Чего не делаем:

- не тянем wordpress-like сложность с ролями, публичным редактором и многопользовательскими сценариями, которых в продукте сейчас нет
- не плодим сложный approval flow
- не заставляем администратора отдельно понимать разницу между draft, preview и publish, если для продукта это не нужно

DoD:

- админ добавил виджет, нажал сохранить и видит его на живом сайте
- система хранит хотя бы короткую историю, чтобы можно было быстро откатиться
- `default reset` возвращает шаблон к исходной безопасной точке

### Этап A. Responsive canvas как честный visual viewport

Цель:

- сделать переключение `desktop / tablet / mobile` наглядным и понятным без чтения технических терминов

Что делаем:

- вводим явный preview-frame с разной шириной и поведением для трех устройств
- визуально отражаем resolver `desktop -> tablet -> mobile`
- показываем inherited/override состояние у выбранного узла
- включаем auto-stack preview для mobile/tablet, если нет override
- делаем row mode `grid / full` заметным прямо на canvas

DoD:

- пользователь без объяснений понимает, что сейчас он смотрит именно tablet или mobile
- mobile/tablet отличаются не подписью, а реальной визуализацией layout
- inherited состояние читается сразу, без похода в документацию

### Этап B. Inspector split: Layout + Style

Цель:

- превратить правую панель из технического мини-редактора в продуктовый inspector

Что делаем:

- разделяем inspector на вкладки `Layout` и `Style`
- в `Layout` оставляем только структуру: ширина, порядок, visibility, stack behavior, row mode
- в `Style` начинаем с MVP-контролов: color, background, spacing, radius, border, shadow, typography basics
- source для `Style` остается тем же `nordicstyl` rules runtime, без второй системы

DoD:

- пользователь меняет layout и стиль в одном месте, но как два понятных слоя
- CSS runtime и builder не дублируют друг друга

### Этап C. Builder-node -> style target

Цель:

- чтобы visual inspector работал от выбора узла на canvas, а не от ручного поиска CSS selector

Что делаем:

- вводим mapping `builder node -> normalized target`
- для выбранного узла inspector показывает человеческое имя и source target
- picker и selector map оставляем как fallback / advanced mode

DoD:

- основной сценарий styling начинается кликом по canvas-узлу
- raw selector не является обязательным знанием для пользователя

### Этап D. Responsive style states

Цель:

- объединить states и devices в одном visual UX

Что делаем:

- вводим switchers `State` и `Device` внутри style-inspector
- сначала поддерживаем `base + mobile` и состояния `default + hover`
- позже расширяем до `tablet`, `active`, `focus` и других состояний

DoD:

- пользователь понимает, меняет ли он базовый стиль или мобильный override
- изменения собираются в тот же CSS runtime без поломки legacy rules

### Этап E. Publish parity без обмана ожиданий

Цель:

- убрать разрыв между тем, что человек видит в builder, и тем, что реально живет на сайте

Что делаем:

- сохраняем desktop publish как текущий stable baseline
- отдельно доводим parity для preview/live
- только после стабилизации layout/view resolver-а расширяем live-публикацию для адаптивных layout-сценариев

DoD:

- builder не обещает того, чего live еще не умеет
- пользователь видит честный результат publish для текущей фазы продукта

### Этап F. Novice-first insertion UX

Цель:

- перестать заставлять новичка мыслить только рядами и колонками

Что делаем:

- поверх текущей структуры добавляем пресеты секций
- даем стартовые сценарии: hero, benefits, cta, faq, contacts
- “Добавить” сначала показывает человеческие блоки, а не только технические типы узлов

DoD:

- пользователь может собрать страницу визуально, не понимая внутреннюю layout-механику InstantCMS

## Приоритет ближайших работ

Если идти без расползания в стороны, правильный порядок такой:

1. Live save foundation: `сохранил = увидел на сайте`, плюс история и reset.
2. Responsive canvas viewport и inherited/override UX.
3. Layout inspector довести до ясного visual поведения по breakpoints.
4. Style inspector MVP поверх существующего `nordicstyl` runtime.
5. Builder-node mapping вместо ручного selector-first сценария.
6. Novice-first presets и insertion flow.

## Что сейчас считать ошибкой направления

- уход обратно в backend-формы как основной UX
- сохранение как обязательный hidden draft-first процесс, который пользователь должен отдельно “публиковать” руками
- попытка сначала “идеально дописать publish”, а потом возвращаться к visual inspector
- расширение технических настроек без улучшения визуальной понятности device-режимов
- параллельное развитие второго builder-а или второго style-продукта рядом с `nordicstyl`
