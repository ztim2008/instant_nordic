# NordicBlocks — Требования К Handoff Готового Кода

## 1. Зачем нужен этот документ

Этот документ описывает, как внешний агент должен передавать уже готовый код блока, чтобы его можно было быстро и безопасно адаптировать в NordicBlocks.

Речь именно про handoff вида:

1. готовый HTML;
2. готовый CSS;
3. при необходимости JS;
4. пояснение, как этот код должен стать block type или preset внутри конструктора.

Этот документ нужен потому, что красивый donor-code сам по себе ещё не означает, что его можно встроить в SSR runtime, inspector и design-token систему NordicBlocks.

## 2. Главный принцип

Внешний агент должен присылать не просто работающий snippet, а адаптируемый snippet.

Хороший handoff-код должен быть:

1. изолированным;
2. семантическим;
3. без глобальных конфликтов;
4. понятным по структуре сущностей;
5. совместимым с design tokens и block runtime.

Важно:

1. допускается и более сырой donor-format, например один HTML-файл со встроенным `<style>`;
2. такой формат не считается идеальным handoff, но считается нормальным входом для адаптации;
3. в этом сценарии я сам отделяю структуру, стили, entity map и token map;
4. чем лучше исходный код и комментарии агента, тем меньше времени уходит на нормализацию;
5. приоритет не в том, чтобы агент сразу знал весь runtime NordicBlocks, а в том, чтобы он дал сильный дизайнерский донорский код без глобального мусора.

## 2.1 Допустимый Упрощённый Формат

Если внешний агент не умеет готовить полный technical handoff, допустимо присылать код в таком виде:

1. один HTML-фрагмент блока;
2. внутри него может быть встроенный `<style>`;
3. без JS, если он не нужен;
4. с локальными классами блока;
5. с коротким текстовым пояснением, что это за блок.

Пример допустимого сырого handoff:

1. `<style>...</style>`
2. `<section class="nb-news-feed">...</section>`

В этом режиме я сам:

1. вычищаю глобальные стили;
2. перевожу код на токены NordicBlocks;
3. решаю, это `content_feed`, `headline_feed`, `category_cards` или новый block type;
4. разбираю item template и entities;
5. адаптирую композицию под SSR/runtime конструктора.

Но даже в упрощённом формате желательно коротко писать:

1. что это за тип блока;
2. нужен ли lead;
3. сколько карточек должно быть видно на desktop;
4. какая подача нужна: журнальная, плотная, editorial, premium, минималистичная;
5. можно ли свободно менять сетку ради лучшей адаптации в NordicBlocks.

## 3. Что обязательно присылать вместе с кодом

Каждый handoff должен содержать 7 частей:

1. `Тип задачи`
   Пример: новый block type, новый preset, перевёрстка существующего блока.
2. `Целевой блок`
   Пример: `headline_feed`, `content_feed`, `category_cards`.
3. `HTML`
   Только разметка секции без внешнего layout страницы.
4. `CSS`
   Только стили блока.
5. `JS`
   Только если без него блок реально не работает.
6. `Entity map`
   Что в коде является section/header/title/subtitle/media/item/meta/button/items.
7. `Responsive note`
   Что должно происходить на desktop/tablet/mobile.

Если какой-то части нет, это нужно написать явно.

Для упрощённого сырого handoff обязательный минимум всё равно должен быть таким:

1. HTML или HTML + CSS;
2. указание, нужен ли JS;
3. краткое описание визуальной цели;
4. указание, это сетка новостей, lead+feed, category cards или другая типология;
5. указание, блок должен быть обычным, акцентным, журнальным, компактным или плотным.

## 4. Формат передачи кода

Код нужно передавать раздельно, а не одной HTML-простынёй со смешанными стилями и скриптами.

Предпочтительный формат:

```md
Задача: [новый блок / preset / перевёрстка]
Целевой block type: [headline_feed / ...]

HTML
```html
...
```

CSS
```css
...
```

JS
```js
...
```

Entity map
1. section -> ...
2. title -> ...
3. items[] -> ...

Responsive
1. desktop -> ...
2. tablet -> ...
3. mobile -> ...
```

Нежелательный формат:

1. один HTML-файл со встроенным всем подряд и без комментариев;
2. screenshot без объяснения, где в коде lead, где repeatable cards;
3. CSS без связи с DOM-структурой;
4. JS без пояснения, зачем он вообще нужен.

Но если задача срочная, такой single-file format всё равно допустим как donor-input, а не как финальный technical handoff.

## 5. Требования К HTML

HTML должен быть:

1. секционным, а не страничным;
2. без header/footer/body/layout сайта;
3. семантическим, где это возможно;
4. пригодным для разрезания на entities и repeater items.

### Что нужно делать

Нужно:

1. использовать `section`, `article`, `h2`, `h3`, `p`, `a`, `button` по смыслу;
2. держать один корневой wrapper блока;
3. группировать повторяемые карточки в отдельный контейнер;
4. отделять lead-card от repeatable cards, если у них разная роль;
5. делать структуру читаемой без лишней вложенности.

### Что нельзя делать

Нельзя:

1. использовать `body`, `main`, `header` сайта как часть handoff;
2. жёстко завязываться на внешний grid страницы;
3. вешать layout на случайные соседние элементы вне блока;
4. использовать ID как основной механизм стилизации;
5. завязывать верстку на позицию элемента в DOM страницы вне блока.

## 6. Требования К CSS

CSS должен быть локальным и адаптируемым.

### Обязательные правила

1. все селекторы должны быть scoped под один корневой класс блока;
2. не использовать глобальные селекторы `body`, `html`, `img`, `a`, `h1`, `h2` без scope блока;
3. не использовать reset, который влияет на весь сайт;
4. не подключать внешние CSS framework-ы;
5. не использовать utility ecosystem вроде Tailwind как обязательное runtime-условие.

### Предпочтительно

1. block root вида `.ref-headline-feed` или `.code-handoff-news`;
2. элементные классы вида `__header`, `__title`, `__grid`, `__card`, `__meta`;
3. модификаторы вида `--lead`, `--compact`, `--cover`, `--split`.

## 7. Требования К Токенам

Если внешний агент уже умеет готовить код под NordicBlocks, он должен использовать токены вместо жёстких значений там, где это разумно.

Базовый набор, на который нужно ориентироваться:

1. `var(--nb-color-bg)`
2. `var(--nb-color-surface)`
3. `var(--nb-color-text)`
4. `var(--nb-color-text-muted)`
5. `var(--nb-color-accent)`
6. `var(--nb-color-border)`
7. `var(--nb-radius-card)`
8. `var(--nb-radius-media)`
9. `var(--nb-shadow-card)`
10. `var(--nb-font-body)`
11. `var(--nb-font-head)`
12. `var(--nb-font-button)`

См. также:

[docs/nordicblocks/GLOBAL-DESIGN-FOUNDATION-V2.md](docs/nordicblocks/GLOBAL-DESIGN-FOUNDATION-V2.md)

### Предпочтительный режим

Лучший вариант handoff:

1. код сразу использует `var(--nb-...)`;
2. локальные переменные блока только переопределяют или группируют токены;
3. нет жёсткой привязки к случайным hex/radius/shadow/font-family.

Пример хорошего подхода:

```css
.ref-news-block {
    --ref-card-bg: var(--nb-color-surface);
    --ref-card-radius: var(--nb-radius-card);
    --ref-title-color: var(--nb-color-text);
    --ref-text-color: var(--nb-color-text-muted);
}
```

### Допустимый fallback-режим

Если агент пока не знает токены NordicBlocks, он должен:

1. собрать все локальные переменные в одном месте;
2. не размазывать raw values по 100 строкам;
3. дать token-map в комментарии или отдельным списком.

Пример:

```css
.ref-news-block {
    --ref-card-bg: #ffffff;
    --ref-title-color: #1e2a3a;
    --ref-accent: #f5a623;
    --ref-radius: 20px;
}
```

И рядом пояснение:

1. `--ref-card-bg` -> `--nb-color-surface`
2. `--ref-title-color` -> `--nb-color-text`
3. `--ref-accent` -> `--nb-color-accent`
4. `--ref-radius` -> `--nb-radius-card`

## 8. Что нельзя хардкодить

Не нужно без необходимости хардкодить:

1. `font-family`;
2. радиусы карточек;
3. тени карточек;
4. базовые цвета текста;
5. базовые surface/background цвета;
6. размеры кнопок, если используется стандартная кнопка.

Это всё должно либо идти через `var(--nb-...)`, либо через один локальный alias-layer.

## 9. Требования К JS

JS допускается только если без него реально не работает механика блока.

### Разрешено

1. небольшой scoped JS для tabs, accordion, toggle, slider-like logic;
2. только block-local selectors;
3. только vanilla JS, если нет очень сильной причины иначе.

### Нельзя

1. подключать jQuery/Swiper/GSAP/CDN-библиотеки как обязательное условие handoff;
2. писать глобальные listeners без scope блока;
3. завязываться на весь документ, если логика относится только к секции;
4. писать код, который ломает SSR, если блок можно сделать без JS.

Если JS всё же нужен, нужно пояснить:

1. зачем он нужен;
2. можно ли деградировать без JS;
3. какие DOM-узлы он ожидает;
4. какие состояния он переключает.

## 10. Требования К Изображениям И Медиа

В handoff-коде надо явно понимать, что является:

1. реальным media slot;
2. временной заглушкой;
3. декоративным фоном;
4. контентным изображением карточки.

Если вместо картинок используются эмодзи, placeholder или серые блоки, это нужно явно пометить как demo-state.

## 11. Entity Map Обязателен

Вместе с кодом должен идти список соответствий между DOM и сущностями конструктора.

Минимальный формат:

1. `section` -> `.ref-news-block`
2. `header` -> `.ref-news-block__header`
3. `title` -> `.ref-news-block__title`
4. `subtitle` -> `.ref-news-block__subtitle`
5. `primaryButton` -> `.ref-news-block__more`
6. `items[]` -> `.ref-news-block__card`
7. `media` -> `.ref-news-block__image`
8. `itemTitle` -> `.ref-news-block__headline`
9. `itemText` -> `.ref-news-block__excerpt`
10. `meta` -> `.ref-news-block__meta`

Без этого адаптация в inspector и contract layer замедляется.

## 12. Требования К Repeatable Элементам

Если код содержит список карточек, внешний агент должен указать:

1. какой элемент является repeatable item;
2. есть ли lead-card и чем он отличается;
3. какие поля в item обязательны;
4. какие элементы optional;
5. как layout ведёт себя, если карточек меньше или больше ожидаемого числа.

## 13. Требования К Responsive Поведению

Вместе с кодом нужно писать, как layout должен жить на breakpoint-ах.

Минимум:

1. desktop: от какой ширины и какая композиция;
2. tablet: что схлопывается и во сколько колонок;
3. mobile: одна колонка или две;
4. какие элементы скрываются или упрощаются;
5. какие тексты clamp/line-clamp обязательны.

Если этого нет, адаптив агенту придётся проектировать заново.

## 14. Что особенно хорошо для NordicBlocks

Лучший handoff-код сразу учитывает, что блок потом будет:

1. жить в SSR;
2. иметь inspector controls;
3. работать в `manual` и иногда в `content_list`;
4. иметь reusable entities;
5. использовать shared block CSS language.

Поэтому внешний агент должен по возможности указывать:

1. где section-level style;
2. где entity-level style;
3. что является reusable card language;
4. что является preset-specific layout;
5. какой кусок можно вынести в shared CSS, а какой только в block-specific слой.

## 14.1 Требование К Визуальному Качеству News-Блоков

Для новостных блоков внешнему агенту лучше сразу ориентироваться не на generic web cards, а на editorial-подачу.

Предпочтительный визуальный вектор:

1. журнальная иерархия;
2. компактная и плотная композиция;
3. выразительная асимметрия там, где она уместна;
4. аккуратная работа с крупной и мелкой карточкой;
5. минимум ощущения `шаблонного AI-блока`.

Нежелательный вектор:

1. одинаковые безопасные карточки без иерархии;
2. слишком много воздуха без редакционного смысла;
3. сетка, похожая на типовой маркетинговый UI kit;
4. визуально стерильная компоновка без характера;
5. блок, который можно перепутать с любым авто-сгенерированным шаблоном.

Если задача касается news/feed family, полезно прямо указывать внешний стиль:

1. `editorial`;
2. `magazine`;
3. `compact newsroom`;
4. `premium content grid`;
5. `dense journal layout`.

Это помогает адаптировать блок ближе к дизайнерской подаче, а не к усреднённой шаблонной сетке.

## 15. Что считается плохим кодовым handoff

Плохой handoff выглядит так:

1. один HTML-файл со встроенным `<style>` и `<script>` без структуры;
2. глобальные селекторы;
3. куча raw colors и font-family по месту;
4. непонятно, где item template;
5. layout зависит от случайных nth-child без объяснения;
6. без описания mobile;
7. без указания, что в блоке главное, а что вторично.

С таким кодом можно работать, но он годится скорее как donor reference, а не как готовый технический handoff.

## 17. Практическое правило

Если внешний агент присылает код, а не скрин, то минимум, который нужен для качественной адаптации:

1. HTML отдельно;
2. CSS отдельно;
3. что является item template;
4. как это живёт на mobile;
5. token map или хотя бы список локальных переменных;
6. пояснение, это новый block type или preset.

Тогда код можно не просто смотреть, а реально быстро переводить в архитектуру NordicBlocks.

## 18. Практический Вывод

Да, можно присылать код даже в более простом формате, например HTML-файл со встроенным CSS, если:

1. код локально scoped;
2. нет глобального мусора;
3. понятно, где карточка и где её контент;
4. визуальная цель описана словами;
5. от меня ожидается именно адаптация под NordicBlocks, а не буквальное копирование donor-кода.

В таком потоке внешний агент может концентрироваться на сильной дизайнерской верстке, а я уже беру на себя:

1. перевод в block runtime;
2. перевод на токены;
3. SSR-разметку;
4. responsive tuning;
5. вписывание в family архитектуру конструктора.
