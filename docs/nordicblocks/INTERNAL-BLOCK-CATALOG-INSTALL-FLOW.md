# NordicBlocks Internal Block Catalog — Install Flow

Дата: 2026-04-23

## 1. Статус документа

Этот документ описывает install flow для будущего внутреннего browser-каталога блоков.

Важно:

1. это продуктовый и архитектурный план;
2. это не кодовый backlog;
3. это не финальный implementation contract;
4. цель документа — заранее зафиксировать безопасную и понятную install-модель.

## 2. Главный принцип

Установка блока из внутреннего каталога должна ощущаться как простой пользовательский шаг,
но архитектурно оставаться локальной установкой,
а не удалённым runtime dependency.

Критическое правило:

после установки блок должен жить локально в компоненте NordicBlocks.

## 3. Базовый install loop

Канонический flow v1:

1. пользователь открывает каталог внутри NordicBlocks;
2. выбирает категорию `Hero`;
3. открывает карточку блока;
4. смотрит preview и краткое описание;
5. нажимает `Установить`;
6. компонент создаёт локально доступный block entry;
7. пользователь получает действие `Открыть в редакторе`;
8. блок редактируется уже через существующий design block editor path.

## 4. Что такое установка в первой волне

В контексте MVP установка должна означать не абстрактное “добавить в избранное”,
а конкретное локальное появление блока внутри компонента.

То есть установка должна приводить к результату:

1. блок появляется в локальном списке доступных блоков;
2. блок можно открыть как normal editable block;
3. блок можно разместить в проекте без повторного похода в каталог.

## 5. Какой install flow предпочтителен архитектурно

Для первой волны предпочтителен такой подход:

1. каталог показывает curated pack metadata;
2. install action переводит block package в локально установленное состояние;
3. редактирование и runtime после этого не зависят от каталога;
4. каталог — это вход в библиотеку, а не обязательная прокладка между блоком и runtime.

## 6. Что пользователь должен понимать в install UX

После нажатия `Установить` у пользователя должно быть ясное ощущение:

1. блок теперь доступен локально;
2. он не исчезнет после закрытия каталога;
3. его можно открыть и править как обычный managed block;
4. установка безопасна и обратима.

## 7. Состояния install flow

Минимально нужны такие состояния:

1. `Не установлен`;
2. `Устанавливается`;
3. `Установлен`;
4. `Ошибка установки`.

В будущем можно добавить:

1. `Доступно обновление`;
2. `Несовместим с этой версией`;
3. `Уже установлен в более новой локальной версии`.

## 8. Что не должно происходить в v1

В install flow первой волны не должно быть:

1. обязательной внешней лицензии;
2. runtime-зависимости от удалённого сервиса;
3. скрытой подмены опубликованного блока после установки;
4. сложной миграционной магии;
5. cloud lock-in для уже установленного free блока.

## 9. Product guardrails

### 9.1 Install must be cheap

Установка должна быть проще, чем ручное создание похожего блока с нуля.

### 9.2 Edit path must stay familiar

После установки пользователь не должен учить новый editor flow.

### 9.3 Catalog is discovery, editor is ownership

Каталог отвечает за выбор и установку.

Editor отвечает за владение, настройку и адаптацию блока.

### 9.4 No hidden premium logic in free MVP

В первом install flow не должно быть псевдо-free UX с последующим paywall.

## 10. Предварительная архитектурная модель

Без кода install flow можно мыслить так:

1. browser layer показывает curated entries;
2. install layer переводит entry в локально установленный asset/block package;
3. registry layer делает этот блок видимым внутри NordicBlocks;
4. editor layer открывает блок уже как обычный managed block.

## 11. Как измерять успех install flow

Установка считается удачной, если:

1. пользователь понимает, что произошло;
2. блок действительно появляется локально;
3. edit path после установки не вызывает когнитивного переключения;
4. install не ощущается как техническая операция администратора;
5. команда может безопасно расширять каталог, не ломая уже установленный контур.
