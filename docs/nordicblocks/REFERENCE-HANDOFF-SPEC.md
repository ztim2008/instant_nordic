# NordicBlocks — Требования К Референсам Для Кодер-Агента

## 1. Зачем нужен этот документ

Этот документ фиксирует, как передавать референсы для новых блоков и перевёрсток, чтобы агент мог быстро и предсказуемо адаптировать их под NordicBlocks, а не гадать по одному скриншоту.

Если вместо скринов передаётся уже готовый HTML/CSS/JS от внешнего агента, использовать отдельный документ:

[docs/nordicblocks/CODE-HANDOFF-SPEC.md](docs/nordicblocks/CODE-HANDOFF-SPEC.md)

Цель:

1. сократить число уточнений;
2. не терять важные детали адаптива и поведения;
3. сразу отделять то, что нужно повторить, от того, что нельзя копировать буквально;
4. давать агенту такой пакет входных данных, который можно сразу превращать в SSR-блок и controls конструктора.

## 2. Главный принцип

Нужен не просто красивый скриншот, а технический референс-пакет.

Хороший референс для агента всегда отвечает на 5 вопросов:

1. что именно нужно собрать;
2. в каком блоке или семействе это должно жить;
3. какая структура секции на desktop/tablet/mobile;
4. что в референсе обязательно сохранить;
5. что можно адаптировать под архитектуру NordicBlocks.

## 3. Минимальный обязательный пакет

Для каждого нового референса нужно передавать:

1. скрин desktop;
2. скрин mobile, если мобильная версия важна;
3. короткое текстовое описание задачи;
4. указание, какой это block type или какой новый block family планируется;
5. список ключевых элементов секции;
6. список важных пропорций и приоритетов;
7. указание, это новый блок или переделка существующего.

Без этого агент почти всегда будет тратить время на догадки.

## 4. Что обязательно писать вместе со скрином

Каждый референс должен сопровождаться текстом в таком виде:

1. `Тип задачи`
   Примеры: новый блок, перевёрстка существующего блока, новый preset, улучшение mobile-layout.
2. `Целевой блок`
   Примеры: `headline_feed`, `content_feed`, `category_cards`, `новый block family`.
3. `Что сохранить`
   Примеры: асимметрию, крупный lead, 2 ряда справа, компактную мету, тёмный overlay.
4. `Что можно менять`
   Примеры: изображения, тексты, точные отступы, декоративные детали, иконки.
5. `Что нельзя делать`
   Примеры: не делать masonry, не использовать слайдер, не тянуть lead на полэкрана, не копировать donor pixel-perfect.

## 5. Требования К Скриншотам

### Desktop

Передавать:

1. полную секцию целиком;
2. без обрезания правого или нижнего края;
3. лучше в ширине 1280-1600 px;
4. без browser chrome, если возможно;
5. без всплывающих cookie/banner overlays.

### Mobile

Передавать:

1. версию шириной примерно 375-430 px;
2. тот же блок, а не соседнюю секцию;
3. если mobile не показан, нужно явно написать `mobile адаптировать самостоятельно`.

### Что плохо

Плохой скрин:

1. секция видна только наполовину;
2. непонятно, где заканчивается блок;
3. не виден низ карточек;
4. нет понимания, один это блок или кусок страницы;
5. референс снят в blur/low quality.

## 6. Что желательно разметить на скрине

Если есть возможность, полезно отметить прямо на изображении:

1. где lead-card;
2. где secondary cards;
3. где CTA или more link;
4. какие карточки должны быть в 1 ряд, а какие в 2 ряда;
5. где важна высота/ширина;
6. какие элементы повторяются;
7. что является отдельным preset, а не новым block type.

Даже простые стрелки и подписи сильно ускоряют работу агента.

## 7. Что важно описывать словами, а не только скрином

Нужно текстом описывать:

1. сколько карточек должно быть видно в типовом состоянии;
2. есть ли жёсткий lead;
3. есть ли `more link`;
4. нужна ли рубрика;
5. нужна ли дата / views / comments;
6. нужна ли тёмная подложка поверх фото;
7. карточки должны быть одинаковой высоты или нет;
8. mobile должен быть в одну колонку или в две;
9. это manual-first блок, data-driven блок или оба режима;
10. это самостоятельный block type или visual preset существующего блока.

## 8. Обязательный Структурный Бриф

Вместе с референсом желательно давать такую структуру:

1. `section header`
   Есть ли заголовок секции, подзаголовок, ссылка справа.
2. `content layout`
   Пример: `1 large lead слева + 2 small cards сверху справа + 1 accent card снизу справа`.
3. `card anatomy`
   Пример: `image, category pill, title, short excerpt, meta`.
4. `density`
   Пример: `компактно`, `воздушно`, `журнально`, `очень плотно`.
5. `tone`
   Пример: `editorial`, `product`, `newsroom`, `lifestyle`, `brutalist`, `minimal`.

## 9. Что особенно важно для NordicBlocks

Поскольку блоки живут в конструкторе, референс должен учитывать не только внешний вид, но и управляемость.

Нужно заранее понимать:

1. это один фиксированный layout или набор presets;
2. нужны ли reusable controls для section/header/media/card/meta;
3. можно ли построить это на уже существующем runtime;
4. нужен ли новый contract shape;
5. какие сущности должны появиться в inspector.

Если этого нет, агенту приходится сначала проектировать архитектуру, а уже потом верстать.

## 10. Что полезно добавить для data-driven блоков

Если блок должен работать в `manual` и `content_list`, у референса нужно описывать:

1. какая карточка становится первой;
2. что происходит, если записей меньше 3;
3. что происходит, если записей больше 6;
4. нужна ли обрезка текста;
5. какие поля обязательны, а какие optional;
6. можно ли скрывать image/meta/category;
7. должен ли layout деградировать gracefully при пустых данных.

## 11. Что полезно передавать кроме скрина

Если есть, это сильно помогает:

1. ссылка на живую страницу-референс;
2. HTML-фрагмент;
3. CSS-фрагмент;
4. Figma frame;
5. отдельные экспортированные изображения карточек;
6. список размеров и отступов;
7. текстовое описание поведения на breakpoint-ах.

Важно:

1. агент не копирует donor дословно;
2. но дополнительные исходники помогают быстрее понять логику композиции.

## 12. Что писать, если нужен именно preset, а не новый block type

Формулировка должна быть прямой:

1. `Это не новый блок, а новый preset для headline_feed`;
2. `Нужно сохранить текущий contract и data layer`;
3. `Меняется только layout и visual hierarchy`;
4. `Новые controls добавлять только если без них preset не живёт`.

Это экономит много времени и защищает от лишнего разрастания block library.

## 13. Быстрый шаблон сообщения для агента

Ниже шаблон, который можно копировать почти без изменений.

```md
Задача: [новый блок / перевёрстка / новый preset]

Целевой block type: [headline_feed / content_feed / category_cards / другой]

Режим: [manual-only / manual + content_list / пока только visual prototype]

Что приложено:
1. desktop screenshot
2. mobile screenshot
3. при наличии ссылка / html / css / figma

Что в референсе главное:
1. [пример: большой lead слева]
2. [пример: справа две строки карточек]
3. [пример: компактная мета]
4. [пример: overlay на фото только у крупных карточек]

Что нужно сохранить обязательно:
1. ...
2. ...

Что можно адаптировать:
1. ...
2. ...

Что нельзя делать:
1. ...
2. ...

Структура секции:
1. header: [есть / нет]
2. layout desktop: [...]
3. layout tablet: [...]
4. layout mobile: [...]
5. card anatomy: [...]

Data-ожидания:
1. первая карточка = ...
2. минимум карточек = ...
3. максимум карточек до деградации = ...

Комментарий:
[любой дополнительный контекст]
```

## 14. Пример хорошей постановки

```md
Задача: новый visual preset для headline_feed

Целевой block type: headline_feed

Режим: manual + content_list

Что приложено:
1. desktop screenshot
2. mobile screenshot нет, mobile адаптировать самостоятельно

Что в референсе главное:
1. крупная главная статья слева
2. справа 2 карточки сверху и 1 акцентная карточка снизу
3. большие карточки с overlay, маленькие без overlay
4. блок должен быть плотным, не гигантским

Что нужно сохранить обязательно:
1. асимметричный editorial layout
2. крупный lead
3. читаемую мету

Что можно адаптировать:
1. размеры шрифтов
2. точные отступы
3. картинки и demo-content

Что нельзя делать:
1. не превращать в masonry
2. не делать слайдер
3. не растягивать lead на половину экрана по высоте

Структура секции:
1. header: заголовок + короткое описание + more link
2. layout desktop: lead слева, справа два ряда
3. layout tablet: lead сверху, карточки сеткой 2 колонки
4. layout mobile: одна колонка
5. card anatomy: image, category, title, optional excerpt, meta
```

## 15. Чего не хватает в плохом референсе

Плохая постановка обычно выглядит так:

1. `сделай как на картинке`;
2. один cropped screenshot без нижней части;
3. нет указания, это новый блок или preset;
4. нет desktop/mobile логики;
5. нет объяснения, что в референсе главное.

С этим можно работать, но получается медленнее и менее точно.

## 16. Практическое правило

Если у вас есть только один скрин, добавьте к нему минимум 5 строк текста:

1. какой block type;
2. какой layout надо получить;
3. что в композиции главное;
4. что нельзя сломать;
5. как это должно вести себя на mobile.

Это уже переводит задачу из режима угадывания в режим инженерной адаптации.
