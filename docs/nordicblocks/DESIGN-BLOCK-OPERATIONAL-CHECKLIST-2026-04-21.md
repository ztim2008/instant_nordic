# NordicBlocks Design Block — Operational Checklist 2026-04-21

Дата: 2026-04-21
Формат: жёсткий утренний runbook на один рабочий день

## 1. Задача дня

Закрыть один честный `v1`-срез `design_block`:

1. add-object flow на canvas;
2. предсказуемое поведение объекта после вставки;
3. element editor с одной понятной IA-моделью;
4. save/reload parity;
5. live widget/runtime smoke.

Если это не закрыто, день нельзя считать завершённым, даже если появятся отдельные новые UI-эффекты.

## 2. Утренний порядок действий

1. открыть [docs/nordicblocks/DESIGN-BLOCK-DAY-PLAN-2026-04-21.md](docs/nordicblocks/DESIGN-BLOCK-DAY-PLAN-2026-04-21.md);
2. открыть рабочий `design_block` editor;
3. проверить текущее рабочее дерево;
4. зафиксировать, что целевой срез дня не менялся.

Что считаем результатом:

1. день начинается не с поиска контекста, а с подтверждённого scope.

---

## Шаг 2. До-кодовый baseline smoke

Что проверить вручную до первого edit-pass:

1. можно ли сейчас добавить новый объект без ручной правки state;
2. что именно происходит после выбора элемента;
3. какие секции реально есть у текущего element editor;
4. как ведут себя drag, resize, guides на уже существующей сцене;
5. как выглядит layers sync;
6. как выглядит текущий save/reload loop.

Что зафиксировать письменно:

1. что уже работает;
2. что сломано или отсутствует;
3. что точно мешает закрыть завтрашний `v1`-срез.

Stop/go правило:

1. не писать код, пока не составлен короткий baseline list из реальных дыр.

---

## Шаг 3. Утренний checkpoint

Когда делать:

1. сразу после baseline smoke и до первого рискованного изменения editor/runtime/save path.

Что считается рискованным:

1. изменения backend actions;
2. изменения normalizer/save path;
3. изменения editor shell, влияющие на add/edit flow;
4. изменения live renderer/runtime parity path.

Что сделать:

1. создать checkpoint через стандартный repo flow;
2. записать snapshot name, commit id и путь к DB dump, если backup создавался.

Stop/go правило:

1. без checkpoint не заходить в backend/runtime проход.

---

## 3. Рабочий маршрут дня

## Блок A. Add-object flow

Цель блока:

1. сделать вставку объектов основным рабочим сценарием дня.

Минимальный список объектов, который надо закрыть:

1. текст;
2. кнопка;
3. shape.

Что сделать по порядку:

1. зафиксировать одну точку входа `Добавить`;
2. описать минимальную palette `v1`;
3. реализовать create action для каждого базового object type;
4. задать стартовые default props и стартовую позицию;
5. после вставки автоматически выбирать новый объект;
6. синхронизировать layers panel.

Что не делать в этом блоке:

1. не пытаться сразу закрыть все типы объектов;
2. не усложнять palette каталогом на десятки элементов;
3. не тянуть asset picker раньше времени.

Контрольная проверка после блока:

1. новый текст можно добавить и сразу редактировать;
2. новая кнопка добавляется и видна на canvas;
3. новый shape появляется в предсказуемом месте;
4. save path не ломается после появления новых элементов.

Checkpoint decision point:

1. если add-object flow потребовал backend/save-path изменения, после первого зелёного прохода оценить, нужен ли второй checkpoint перед element editor IA.

---

## Блок B. Поведение объектов на canvas

Цель блока:

1. убедиться, что объект после вставки ведёт себя как нормальная рабочая сущность, а не как статический JSON-узел.

Что проверить и добить:

1. selection сразу после insertion;
2. drag start без лишних кликов;
3. resize handles по типу объекта;
4. guides и snap после insertion;
5. sibling alignment в реальном authoring loop;
6. negative `x` и bleed;
7. layers sync при выборе и перемещении.

Обязательные unit smoke после правок:

1. interaction core tests;
2. geometry core tests, если затронута guide/world math.

Stop/go правило:

1. если объект нельзя стабильно вставить, выбрать и сдвинуть, дальше в element editor идти нельзя.

---

## Блок C. Element editor IA

Цель блока:

1. сделать один канонический редактор выбранного элемента.

Обязательная структура editor-а:

1. `Контент`;
2. `Макет`;
3. `Стиль`.

Что должно быть доступно как минимум:

1. текст: content, basic typography, color, width/height, x/y;
2. кнопка: label, placeholder url, colors, radius, padding, width/height, x/y;
3. shape: fill, radius, stroke basics, width/height, x/y.

Обязательные quick actions:

1. дублировать;
2. удалить;
3. поднять/опустить слой, если это уже доступно без большой архитектурной боковой ветки.

Что не делать:

1. не плодить разные правые панели под каждый object type;
2. не уводить частые настройки глубоко;
3. не строить giant settings panel из редких полей.

Контрольная проверка после блока:

1. один и тот же inspector читается одинаково для текста, кнопки и shape;
2. основные изменения сразу видны на canvas;
3. `canvas -> inspector -> layers` и обратно остаются синхронны.

Checkpoint decision point:

1. если после IA-рефакторинга изменился большой кусок editor shell, перед save/reload hardening лучше сделать ещё один checkpoint.

---

## Блок D. Save/reload hardening

Цель блока:

1. доказать, что новый add/edit flow живёт не только в текущей сессии editor.

Обязательный сценарий:

1. создать сцену через новый UI-flow;
2. добавить минимум текст, кнопку и shape;
3. изменить их через inspector;
4. сделать один nested или alignment кейс;
5. сохранить;
6. перезагрузить editor;
7. убедиться, что сцена восстановилась корректно.

Что проверить явно:

1. normalizer не теряет новые default props;
2. transient editor state не сохраняется в contract;
3. grid fields, bleed и box coordinates не деградируют;
4. layers order сохраняется.

Stop/go правило:

1. без зелёного save/reload день нельзя переводить в live runtime phase.

---

## Блок E. Widget/live parity smoke

Цель блока:

1. подтвердить, что новый authoring loop реально живёт вне editor shell.

Обязательные smoke-сценарии:

1. разместить рабочий `design_block` через стандартный widget flow;
2. открыть публичную страницу;
3. проверить desktop layout;
4. проверить mobile или narrow viewport layout;
5. проверить минимум один bleed/negative-x кейс;
6. проверить, что порядок слоёв и базовые размеры не расходятся с editor;
7. убедиться, что editor-only assets не протекают в public runtime.

Что считается проходом:

1. layout в live не «примерно похож», а предсказуемо совпадает по ключевым координатам и размерам;
2. нет PHP warnings и нет явной visual деградации.

---

## Блок F. Stretch goal, только если всё зелёное

Что допускается только после A-E:

1. image object или image picker start;
2. container insertion, если он действительно нужен как следующий честный слой.

Что не допускается:

1. уходить в asset integration, если add/edit/save/live loop ещё шаткий.

---

## 4. Обязательные smoke-сценарии дня

К вечеру обязательно должны быть пройдены именно эти сценарии:

1. add text -> edit text -> save -> reload;
2. add button -> edit label/style -> drag -> save -> reload;
3. add shape -> resize -> save -> reload;
4. sibling alignment snap на сцене, собранной уже новым UI-flow;
5. bleed или negative-x кейс без деградации после reload;
6. widget placement и live page render рабочего блока.

Если любой из этих smoke не пройден, день не считается закрытым.

---

## 5. Где ставить checkpoint-ы

Обязательные checkpoint-моменты:

1. утром после baseline и до первого рискованного edit-pass;
2. перед крупным рефакторингом editor shell, если add-flow уже заработал;
3. перед изменениями backend save/runtime path, если они понадобятся для parity;
4. опционально в конце дня, если получился реально устойчивый slice и нужна удобная точка возврата.

Checkpoint не обязателен перед каждой мелкой правкой, но обязателен перед каждым изменением, которое может сломать backend flow или live runtime.

---

## 6. Чёткий критерий завершения дня

Завтрашняя задача считается закрытой только если одновременно верно всё ниже:

1. базовые объекты добавляются на canvas без ручной правки state;
2. объект после вставки можно сразу выбрать, двигать и редактировать;
3. есть один понятный element editor с секциями `Контент`, `Макет`, `Стиль`;
4. работают delete и duplicate;
5. save/reload возвращает ту же сцену;
6. live runtime не разваливает сцену, собранную новым authoring flow.

---

## 7. Если день идёт тяжело

Порядок урезания scope такой:

1. сначала убрать всё лишнее и закрыть только text/button/shape;
2. потом отложить image picker;
3. потом отложить container insertion;
4. но не отдавать день без save/reload и live parity.

Главное правило:

1. лучше закрыть маленький, но честный product slice, чем собрать много полуготовых режимов.
