# NordicBlocks — План расширенных настроек на 2026-04-18

## Зачем это делаем

Сейчас editor shell уже стал достаточно тонким и управляемым, чтобы без боли добавлять не только текст и базовые параметры, но и нормальные дизайнерские ручки.

Цель следующего дня:

1. добавить в inspector не случайные разовые поля, а понятный набор визуальных настроек;
2. сделать так, чтобы эти настройки работали одинаково в `hero`, `faq` и следующих блоках;
3. превратить редактор из «поправить текст» в более полноценный инструмент сборки продающего блока.

## На что опираемся

Этот документ не придумывает новый канон с нуля, а продолжает уже существующие решения из:

1. `BLOCK-DESIGN-MANIFEST-V1`;
2. `GLOBAL-DESIGN-FOUNDATION-V2`;
3. `UNIFIED-INSPECTOR-ARCHITECTURE`.

Главный принцип:

если настройку можно выразить как shared control или через global design system, не надо делать новую одноразовую ветку только для одного блока.

## Что именно хотим добавить первым приоритетом

### 1. Секция

Это даёт самый быстрый визуальный результат и почти всегда полезно.

Что включаем в первый проход:

1. фон секции: `theme | solid | gradient | image`;
2. overlay color и overlay opacity;
3. background position / size / repeat там, где уже есть image mode;
4. padding top/bottom для desktop/mobile;
5. content width preset и custom max width;
6. align контейнера;
7. section surface radius, если секция визуально работает как плашка;
8. section shadow preset, если секция должна читаться как отдельная поверхность.

Что это даст в работе:

1. можно быстро собирать «воздушные» и «плотные» секции без правки шаблонов;
2. проще делать hero и faq не похожими друг на друга;
3. меньше причин идти в CSS ради обычных визуальных правок.

### 2. Плашки / карточки / поверхности

Это второй слой пользы после секции.

Что включаем в первый проход:

1. surface background;
2. border color;
3. border width;
4. border radius;
5. shadow preset;
6. inner padding;
7. gap между внутренними элементами, если поверхность является контейнером.

Что это даст в работе:

1. FAQ можно быстро делать как мягкие карточки, строгие рамки или почти невидимые поверхности;
2. hero-media и сопутствующие блоки получают нормальную глубину без ручного CSS;
3. появляется база для единого visual language, а не для разрозненных локальных хаков.

### 3. Компоновка и расстояния

Это не так заметно в списке настроек, но очень заметно в результате.

Что включаем в первый проход:

1. gap между элементами внутри секции;
2. gap между карточками/repeater items;
3. margin bottom у ключевых сущностей, если его ещё не хватает в shared controls;
4. desktop/mobile overrides там, где они уже соответствуют текущей runtime-модели.

Что это даст в работе:

1. блоки перестанут выглядеть «слипшимися»;
2. меньше ручных правок spacing после каждого нового контентного кейса;
3. проще добиваться аккуратной мобильной версии.

## Что не тащим в первый проход

Чтобы не размыть день, сознательно не берём:

1. сложный multi-layer background builder;
2. shape dividers;
3. анимационный composer;
4. слишком детальный per-side visual editor для всего сразу;
5. одноразовые настройки, которые нужны только одному частному блоку.

## Как раскладываем это по inspector

### Дизайн

Сюда идут:

1. background;
2. overlay;
3. surface background;
4. border;
5. radius;
6. shadow;
7. opacity там, где это действительно visual control.

### Макет

Сюда идут:

1. width;
2. padding;
3. gap;
4. alignment;
5. desktop/mobile overrides.

### Контент

Сюда не смешиваем визуальные свойства, кроме случаев, когда это реально содержимое, например текст плашки или label.

## Практический порядок работы на завтра

1. Проверить, какие из нужных настроек уже частично есть в shared controls, чтобы не дублировать существующее.
2. Собрать минимальный канонический набор shared controls для section, surface и spacing.
3. Подключить этот набор к `hero` и `faq` через текущий manifest/control pipeline.
4. Довести renderer/runtime до состояния, где эти настройки реально видны и сохраняются одинаково.
5. Прогнать короткий smoke на реальном каноническом потоке.

## Минимальный Definition of Done на день

День можно считать удачным, если одновременно выполнено всё ниже:

1. в editor есть понятный первый набор расширенных visual controls;
2. минимум `hero` и `faq` используют его по одному и тому же принципу;
3. настройки сохраняются, повторно открываются и реально меняют preview;
4. новые поля не плодят новый giant-runtime и не ломают current composition-shell подход.

## Самый полезный результат для продукта

Если сделать этот проход нормально, редактор начнёт давать не только структурное редактирование, но и реальную визуальную сборку блока:

1. можно будет быстро собирать более «дорогой» внешний вид блока прямо из админки;
2. меньше правок через код и CSS ради обычных дизайнерских задач;
3. следующий блок будет проще запускать, потому что visual controls уже станут частью общей системы, а не разовой доработкой.
