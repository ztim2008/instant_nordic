# NordicBlocks Worklog — 2026-04-17

## Что зафиксировано сегодня

Сегодня подтверждён стратегический вектор следующей итерации NordicBlocks.

Главная цель: доказать, что один и тот же SSR runtime одинаково обслуживает:

1. `manual` блок;
2. `content_item` блок;
3. `content_list` блок.

## Ключевое правило продукта

Не все блоки обязаны использовать данные системы.

Это зафиксировано как постоянное проектное правило:

1. `manual-first` блоки остаются нормальным и целевым сценарием;
2. data adapters нужны только тем блокам, где есть реальная системная ценность;
3. отсутствие adapter-слоя не считается недостатком для block type, если он должен быть статичным по смыслу.

### Примеры

1. Блок новостей, статей, кейсов, карточек контента:
  - да, это data-driven сценарий.
2. Блок преимуществ, trust-секция, оффер, простой CTA:
  - нет, ему чаще всего не нужны данные из InstantCMS.

## Что это даёт в реальной работе

1. Сначала усиливается ядро системы, а не расползается библиотека блоков.
2. После этого любой следующий dynamic block будет подниматься быстрее и чище.
3. Manual-first блоки не будут страдать от навязанной data-логики там, где она не нужна.
4. Первый нормальный content-list block будет строиться уже на зрелом runtime, а не на временном прототипе.

## Следующий практический шаг

Если продолжать сразу по коду, начинать с `hero + content_item` и только потом возвращаться к новому list-output block.

## Что уже закрыто по коду

1. `hero` поднят на `content_item` через тот же hydration pipeline, что уже работал для `faq + content_list`.
2. Вкладка `Данные` больше не завязана на FAQ-термины: первый panel теперь работает как общий source layer для single и list сценариев, а item-level mapping вынесен в отдельную generic collection panel.
