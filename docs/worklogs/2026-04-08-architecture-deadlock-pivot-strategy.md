# 2026-04-08 — Deadlock и стратегический поворот к коммерческой надстройке

## Стратегическое решение

Принято решение развивать продукт как коммерческий компонент-надстройку для InstantCMS.

Ключевой принцип:

1. не трогаем ядро системы и не завязываем развитие на правки core;
2. минимизируем вмешательство в шаблонную базу движка;
3. строим собственный предсказуемый canvas/runtime слой, который получает от InstantCMS только нужные данные через адаптеры.

Ожидаемый эффект:

1. проще обновлять движок и шаблон;
2. меньше регрессий от legacy-веток;
3. стабильная упаковка в installable zip и обновления по версиям.

## Зафиксированный тупик

Сегодня зафиксирован инженерный тупик по текущему bridge-слою canvas:

1. часть сценариев работает нестабильно и непредсказуемо между маршрутами;
2. часть настроек inspector не влияет на canvas/runtime так, как ожидается;
3. есть расхождение между админским состоянием и реальным frontend-подбором страницы;
4. накопились устаревшие ветки (legacy fallback, обходы и частичные режимы), мешающие диагностике.

## Симптомы, подтвержденные в работе

1. настройки inspector визуально есть, но часть параметров не доходит до эффективного runtime;
2. после создания страниц привязка к контентным маршрутам может срабатывать нестабильно;
3. смешаны несколько путей выбора страницы/режима (legacy fallback, bindings, overlay hooks, template fallback);
4. различия поведения admin/guest создают лишний шум на этапе стабилизации.

## Что сохраняем

1. visual-first смысл продукта;
2. canvas как основной рабочий экран;
3. идея кастомных блоков и блоков-адаптеров под данные InstantCMS;
4. единый результат preview/live;
5. упаковка компонента как коммерческого дистрибутива.

## Что меняем архитектурно

### 1. Компонент как надстройка без вмешательства в ядро

Цель: полностью убрать зависимость от правок системного ядра как источника развития.

Правила:

1. InstantCMS рассматривается как стабильный backend-провайдер данных и маршрутов;
2. наш компонент владеет canvas, блоками, binding-правилами и runtime-отрисовкой;
3. адаптеры забирают контекст и данные, но не меняют поведение ядра.

### 2. Canvas-first ядро как приоритет №1

Цель: сначала собрать профессиональный адаптивный canvas без технической боли для пользователя.

Базовые требования:

1. drag-and-drop секций;
2. сетка секции на основе 12-колоночной модели и режима 100%;
3. интерактивное изменение ширин колонок с автопересчетом адаптивности;
4. действия как в Instant-практике: добавить ряд, дублировать, скрыть, редактировать, удалить;
5. отдельные настройки секции/сетки в inspector (padding и другие понятные control-поля).

### 3. Логика размещения как в Instant, но в нашем компоненте

Цель: зеркалить предсказуемую модель размещения, не копируя технический шум.

Принципы:

1. поддержка сценариев: главная, все страницы, список контента, запись контента;
2. корректная работа «тела системы» как системного контент-слота, а не только кастомных блоков;
3. поддержка сквозных секций (например, логотип/меню/авторизация), если секция помечена как глобальная;
4. правила применения страниц упрощены до dropdown/checkbox-first UX.

### 4. Inspector cleanup и жесткая дисциплина control-полей

Цель: убрать все, что не влияет на результат.

Правила:

1. любой control в inspector либо влияет на runtime, либо удаляется;
2. статусы полей: active / noop / deprecated;
3. скрыть/удалить шумные опции на текущем этапе (пример: «вертикальный ритм», «пресет контейнера», лишние технастройки секции);
4. все сложные параметры только по необходимости и с понятной подсказкой.

### 5. Упрощение surface-модели на текущем этапе

Цель: сократить сложность до рабочего ядра canvas.

Решения:

1. shell-логику и пресеты временно выводим из критического пути разработки;
2. технические правила применения и bindings сводим на одну страницу с понятным русским объяснением;
3. различия admin/guest временно не являются приоритетом до стабилизации pipeline.

## Целевая модель pipeline выбора страницы

Один детерминированный путь вычисления effective page key:

1. route context;
2. explicit binding match;
3. overlay branch только для overlay-маршрутов;
4. controlled fallback;
5. запрет неявных legacy-веток.

## Product scope canvas (версия «по-взрослому»)

1. desktop/tablet/mobile переключатели как обязательная часть работы;
2. библиотека блоков через модальное окно;
3. кастомные блоки на canvas должны выглядеть близко к live;
4. блоки-адаптеры и «тело системы» допускают специальный preview-режим там, где live-данные плавающие;
5. глобальная дизайн-система (типографика, отступы, тени, скругления) плюс локальные настройки блока.

## Dashboard как первый экран

Первый экран конструктора фиксируется как dashboard:

1. количество страниц;
2. количество блоков;
3. статус canvas;
4. быстрый вход в рабочую канву.

## Антикризисный план

### Фаза A — Freeze и диагностика (P0)

1. freeze новых фич до завершения аудита;
2. собрать route matrix: homepage, content list, content item, content category, user profile;
3. для каждого маршрута зафиксировать: какой page key выбран, почему и каким код-путем.

### Фаза B — Архитектурный cut

1. выделить единый резолвер effective page key;
2. удалить дублирующие fallback-ветки;
3. ввести debug trace выбора ветки для dev.

### Фаза C — Inspector sanity pass

1. пройти все controls inspector;
2. исключить controls без эффекта;
3. привязать оставшиеся controls к проверяемому runtime-output.

### Фаза D — Canvas UX hardening

1. довести grid/sections/drag-resize до предсказуемого состояния;
2. закрепить mobile/tablet/desktop поведение;
3. упростить page creation flow до dropdown/checkbox сценариев.

### Фаза E — Packaging and updates

1. release как installable zip;
2. versioning и update-пакеты без правок ядра;
3. стабильный upgrade path для клиентов.

## Definition of Done (обновлено)

1. новая страница стабильно применяется к целевым маршрутам;
2. для каждого route context выбор страницы детерминирован и объясним;
3. в inspector нет полей без эффекта;
4. preview/live дают одинаковый результат по одной схеме;
5. canvas поддерживает desktop/tablet/mobile и предсказуемую адаптивность;
6. правила применения страницы настраиваются без технической боли;
7. компонент собирается в коммерческий zip и обновляется без вмешательства в ядро InstantCMS.

## Риски

1. без архитектурного cut продолжится наращивание заплаток;
2. пересечение legacy-веток будет давать ложные регрессии;
3. сохранится недоверие к inspector/canvas;
4. без жесткой политики «не трогаем ядро» снова вырастет стоимость обновлений.

## Точка отката

Актуальная точка отката: отдельный checkpoint перед стартом архитектурного рефактора.

## Следующий рабочий шаг

1. утвердить короткий RFC «Коммерческая надстройка без правок ядра»;
2. начать P0-аудит route matrix и полную инвентаризацию inspector controls;
3. затем перейти к коду рефактора строго по фазам A-E.
