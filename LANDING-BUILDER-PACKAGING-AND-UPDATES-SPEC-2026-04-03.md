## 1. Цель документа

Этот документ фиксирует, что конечный результат проекта должен быть не только кодом компонента, а полноценным цифровым продуктом с:

1. installable package;
2. frontend template;
3. update-пакетами;
4. версионированием;
5. release discipline.

## 2. Базовый принцип

### 🟢 Готово: принцип зафиксирован

Нордик должен проектироваться сразу как продаваемый цифровой продукт для InstantCMS 2.

Это означает, что с первого этапа проектирования нужно учитывать:

- первую установку на чистый сайт;
- обновление уже установленного продукта;
- совместимость версий;
- миграции данных;
- выпуск release-архивов.

## 3. Что входит в поставку продукта

### 🔵 В работе: модель поставки зафиксирована

Продукт должен состоять минимум из трех частей.

### 3.1. Компонент `landingbuilder`

Назначение:

- backend;
- frontend runtime логика;
- bindings;
- registry;
- editor;
- presets;
- page versions;
- update logic компонента.

### 3.2. Шаблон `nordic`

Назначение:

- отдельный frontend template InstantCMS;
- должен быть доступен в системных настройках сайта как шаблон по умолчанию;
- выступает базовым runtime-shell для продукта Нордик;
- может использовать `modern` как технический предок или как референс для реализации.

### 3.3. Пакеты блоков

Назначение:

- расширение библиотеки блоков;
- продажа и обновление отдельных наборов;
- тематические collections.

## 4. Архитектурный вывод

### 🟢 Готово: решение пересмотрено

Предыдущее решение "конструктор не должен появляться как шаблон по умолчанию" для этого проекта больше не актуально.

Новая модель такая:

1. `landingbuilder` живет как отдельный компонент;
2. `nordic` живет как отдельный frontend template;
3. в настройках сайта пользователь может выбрать `nordic` как шаблон по умолчанию;
4. сам конструктор при этом продолжает иметь собственный backend и собственные сущности.

Итого:

- продукт = не только компонент;
- продукт = template + component + installer + updates.

## 5. Механизм установки

### 🟡 Запланировано

На первую установку нужны:

1. install package компонента `landingbuilder`;
2. install package шаблона `nordic`;
3. начальная регистрация block manifests и adapter manifests;
4. начальная SQL-структура builder;
5. начальный preset layer;
6. документация по установке и первому запуску.

## 6. Механизм обновлений

### 🟡 Запланировано

Обновления должны проектироваться сразу.

Минимальные требования:

1. У каждого release есть версия.
2. У install package и update package есть совместимость по версиям.
3. SQL-изменения идут через update discipline, а не через ручные правки.
4. Block packs должны иметь свою версию и матрицу совместимости с core.
5. Обновление не должно терять страницы, presets, bindings и registry state.

## 7. Типы выпусков

### 🟡 Запланировано

Нужны как минимум такие типы release:

1. Full install release.
2. Component update release.
3. Template update release.
4. Block pack release.
5. Hotfix release.

## 8. Версионирование

### 🟡 Запланировано

Рекомендуемая модель:

- core component version;
- template version;
- blocks pack version;
- JSON contracts schema version;
- page schema version.

На практике это значит, что breaking changes в contracts и runtime нельзя смешивать с обычными patch updates.

## 9. Что нужно заложить в разработке с самого начала

### 🔵 В работе: требования зафиксированы

При реализации skeleton сразу учитывать:

1. версию компонента;
2. версию шаблона;
3. install/update hooks;
4. диагностику несовместимых pack versions;
5. release notes и changelog discipline;
6. точку миграции данных между версиями.

## 10. Роль instantcms-mcp-main

### 🟢 Готово: роль зафиксирована

Папка [instantcms-mcp-main](instantcms-mcp-main) в корне проекта является основной dev-базой для разработки.

Она используется как:

1. reference по InstantCMS internals;
2. scaffolding база;
3. источник patterns для package/install/update flow;
4. набор инструментов для безопасного анализа существующей платформы.

При проектировании и разработке Нордик нужно опираться на нее как на основной технический reference-пакет в этом workspace.
