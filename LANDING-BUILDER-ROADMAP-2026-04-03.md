## 1. Короткий ответ на вопрос про WordPress

Да, по смыслу это похоже на правку шаблона и page builder в WordPress, но архитектурно не совсем одно и то же.

Похоже в том, что:

- есть тема оформления;
- есть визуальная сборка страниц из блоков;
- есть библиотека готовых секций;
- есть отдельная логика для контента и отдельная для отображения.

Отличается тем, что в InstantCMS уже есть:

- dynamic layout;
- система виджетов и позиций;
- типы контента и поля;
- шаблоны контроллеров и widget overrides;
- SCSS middleware и theme options.

Поэтому здесь правильнее думать не как о простом редакторе темы, а как о новом конструкторе страниц, встроенном в экосистему InstantCMS и использующем тему `modern` как базу рендера и дизайна.

## 2. Цель проекта

Сделать внутри InstantCMS современный и понятный для пользователя конструктор лендингов:

- с drag-and-drop секциями;
- с библиотекой готовых блоков по категориям;
- с визуальным canvas-preview;
- с ручным и динамическим наполнением;
- без показа пользователю Bootstrap-терминов и служебной структуры layout.

## 3. Рекомендованный архитектурный путь

Текущая рекомендация:

- делать не просто правку темы `modern`;
- делать отдельный устанавливаемый компонент-конструктор;
- делать отдельный frontend template `nordic`, который выбирается в настройках сайта как шаблон по умолчанию;
- использовать `modern` как reference и базу для наследования архитектурных решений шаблона;
- не использовать текущую админскую сетку rows/cols/widgets как конечный интерфейс пользователя;
- сразу закладывать расширяемую систему блоков, которые могут поставляться отдельно от ядра конструктора.

Итого:

- core = отдельный installable component;
- template = отдельный frontend template `nordic`;
- editor = часть компонента;
- rendering = внутри продукта Нордик, с опорой на `modern`;
- блоки = отдельная библиотека секций и partial templates;
- data binding = через типы контента, категории, query collections, route context и ручные данные;
- block packs = отдельные расширения, совместимые с ядром конструктора.

## 3.1. Важное продуктовое уточнение

Нордик должен быть не только page builder, а visual content composition system.

Это значит:

1. Любой подходящий блок может брать данные из content type.
2. Один и тот же блок карточек должен уметь работать как с ручными карточками, так и с динамической выборкой.
3. Страница сайта должна подключаться к builder полностью, частично или только по зонам.
4. Для живого проекта важнее безопасное постепенное внедрение, чем тотальный takeover всех страниц сразу.

## 3.2. Важное UX-уточнение по canvas

Нордик должен быть полностью визуальным на холсте.

Это значит:

1. на странице может быть много секций, а не одна;
2. секции должны поддерживать 1, 2 и 3 колонки;
3. элементы должны перетаскиваться между колонками drag-and-drop способом;
4. у редактора должны быть device toggles: desktop, tablet, mobile;
5. стандартные widgets InstantCMS тоже должны добавляться на холст;
6. текущая система InstantCMS `row -> col -> position -> widget` должна использоваться как внутренний reference, но не как пользовательский UX.

## 4. Дополнительная стратегическая идея: ядро + пакеты блоков

Конструктор лучше проектировать сразу в двух слоях:

1. Ядро конструктора.
2. Отдельные пакеты блоков.

### Ядро конструктора

Ядро должно поставляться как полноценный компонент InstantCMS по всем правилам создания компонентов:

- со своим frontend и backend;
- со своими таблицами и настройками;
- с installable package;
- с поддержкой update-пакетов;
- с корректным uninstall или cleanup-логикой.

Это важно, потому что конструктор потом должен ставиться на другие проекты InstantCMS без ручной сборки.

### Шаблон продукта

Отдельно от компонента должен поставляться frontend template `nordic`.

Это важно потому что:

- пользователь должен видеть Нордик в системных настройках шаблона сайта;
- продукт должен уметь работать как полноценный frontend-shell;
- дальнейшие обновления шаблона должны выпускаться отдельно от обновлений компонента, когда это нужно.

### Пакеты блоков

Блоки не стоит зашивать навсегда внутрь ядра.

Лучше сразу заложить архитектуру, в которой:

- есть базовый набор блоков в ядре;
- дополнительные блоки могут устанавливаться отдельно;
- блоки могут поставляться тематическими коллекциями;
- эти коллекции можно выпускать и монетизировать отдельно.

Рекомендуемая модель:

- core component;
- base blocks pack;
- premium blocks packs.

### Как это лучше маппить на InstantCMS

С точки зрения механики пакетов InstantCMS:

- ядро конструктора = пакет установки компонента;
- дополнительные блоки = отдельные installable packages с зависимостью от компонента-конструктора;
- такие пакеты не обязательно должны регистрироваться как обычные виджеты CMS;
- они могут устанавливаться как общие или системные пакеты, копировать свои manifests, templates, assets и при необходимости регистрировать блоки через `install.php`.

Почему лучше не делать их обычными widget packages:

- блок конструктора и системный widget InstantCMS по смыслу не одно и то же;
- иначе стандартная палитра виджетов начнет смешиваться с библиотекой блоков конструктора;
- это ухудшит UX и архитектурную чистоту продукта.

## 6. Как это должно выглядеть в настройках InstantCMS

### 🧪 На проверке: решение пересмотрено

Здесь важно не повторить модель WordPress один в один.

В InstantCMS глобальный шаблон сайта выбирается в системных настройках как один активный frontend template. Для проекта Нордик это больше не считается ограничением, которое нужно обходить стороной.

Новая продуктовая модель:

- тема сайта по-прежнему выбирается одна;
- в нашем случае пользователь должен иметь возможность выбрать `nordic` как шаблон по умолчанию;
- сам builder продолжает жить как отдельный компонент `landingbuilder`;
- итоговый продукт работает как связка template + component.

### Что это значит practically

Для этого проекта правильный путь такой:

- пользователь выбирает `nordic` как frontend template сайта;
- отдельно устанавливает и обновляет компонент `landingbuilder`;
- затем управляет страницами, bindings и библиотекой блоков через backend компонента.
- затем решает для каждой страницы режим участия: full page, hybrid overlay или zone injection.

### Практический пример динамического блока

Нужный сценарий для MVP:

- на страницу добавляется блок карточек;
- в настройках блока выбирается источник `Объявления`;
- блок динамически подгружает карточки этого ctype;
- при желании тот же блок можно переключить в ручной режим или на другой источник.

### Рекомендуемая модель настроек

#### 1. Глобальные настройки сайта

Оставить как есть:

- активная тема сайта;
- mobile/tablet/dev template;
- опции самой темы.

Здесь должен появляться template `nordic` как штатный selectable template продукта.

#### 2. Отдельный раздел в админке компонента

У конструктора должен быть свой backend-раздел, например:

- список страниц конструктора;
- библиотека блоков;
- block packs;
- adapters;
- глобальные настройки конструктора;
- style presets;
- bindings.

Это должен быть нормальный backend компонента InstantCMS, а не вкладка внутри выбора шаблона сайта.

#### 3. Глобальные настройки конструктора

Внутри самого компонента нужны отдельные настройки, например:

1. Базовая тема рендера.
2. Разрешённые adapters.
3. Включён ли styling overlay.
4. Включён ли structural overlay.
5. Какие block packs активны.
6. Какие style token groups доступны редактору.

На первом этапе базовая тема рендера может быть ограничена только `modern`.

#### 4. Настройки привязки по страницам

Нужно сделать не замену темы, а систему bindings.

То есть отдельно управлять:

1. standalone landing pages;
2. homepage;
3. page adapters для системных страниц;
4. opt-in для content types;
5. правила применения overlay к конкретным типам страниц.

#### 5. Настройки в типе контента

Для пользовательских content types нужно отдельное opt-in поведение в настройках ctype:

1. участвует ли тип контента в конструкторе;
2. поддерживается ли item page;
3. поддерживается ли list page;
4. поддерживается ли category page;
5. какой adapter использовать;
6. какой preset токенов использовать по умолчанию.

### Итоговая модель для пользователя

У пользователя должно быть три разных уровня управления, а не один селект темы.

#### Уровень 1. Тема сайта

- выбирается один раз в общих настройках сайта;
- отвечает за общий frontend-shell.

#### Уровень 2. Конструктор

- включается как отдельный компонент;
- управляет страницами, блоками, adapters и библиотекой секций.

#### Уровень 3. Привязки

- определяют, где именно конструктор участвует:
   - отдельная landing page;
   - главная;
   - страница материала;
   - страница категории;
   - профиль;
   - пользовательский content type.

### Самый важный вывод

Конструктор не должен исчезать внутри одной только темы.

Итоговая модель продукта должна быть такой:

- template `nordic` доступен как шаблон по умолчанию;
- component `landingbuilder` живет отдельно и управляет:

- рендером отдельных страниц;
- overlays;
- библиотекой блоков;
- page adapters;
- style tokens.

Именно так архитектура будет совместима с InstantCMS и понятна пользователю.

### 🔴 Этап 7.1. Спроектировать участие готовых страниц сайта в конструкторе

Статус: запланировано.

Цель этапа:

- определить, как конструктор будет работать не только с отдельными лендингами, но и с уже существующими страницами сайта: материалами, профилями, архивами, страницами пользовательских типов контента.

Здесь нужно разделить два режима:

1. Styling overlay для готовой страницы.
2. Structural overlay для готовой страницы.

### Styling overlay

Это режим, в котором пользователь в боковой панели может менять:

- шрифты;
- размеры и отступы;
- цвета текста;
- цвета кнопок;
- фон и карточки блоков;
- радиусы;
- тени;
- акцентные состояния.

Такой режим реалистично поддержать для многих страниц сайта.

Рекомендуемый принцип реализации:

- не пытаться пересобирать SCSS на каждое изменение страницы;
- использовать page-level CSS variables и style tokens;
- навешивать их на wrapper конкретной страницы или конкретной зоны.

Это особенно подходит для:

- страницы материала;
- страницы профиля;
- списков материалов;
- страниц категорий;
- типовых системных экранов с понятной структурой.

### Structural overlay

Это режим, в котором пользователь не просто красит существующую страницу, а реально управляет секциями поверх готовой страницы.

Такой режим тоже возможен, но не универсально “автоматом” для всех страниц.

Для него нужны page adapters:

- adapter для страницы материала;
- adapter для профиля;
- adapter для списка контента;
- adapter для категории;
- adapter для специальных системных страниц.

Каждый adapter должен отдавать не произвольный DOM, а контролируемые editable zones, например:

- hero area;
- top section;
- sidebar;
- before content;
- after content;
- CTA area;
- related content zone.

Критически важно:

- не редактировать “всю страницу через любой DOM-узел”;
- а описывать для каждого типа страницы допустимые области управления.

Результат этапа:

- карта поддерживаемых page types;
- список adapters и editable zones;
- решение, где доступен только styling overlay, а где доступен и structural overlay.

Критерий готовности:

- ясно, какие страницы конструктор умеет стилизовать, какие умеет структурно расширять, а какие пока не поддерживаются.

### 🔴 Этап 7.2. Спроектировать участие пользовательских типов контента

Статус: запланировано.

Цель этапа:

- сделать так, чтобы любые типы контента, созданные пользователем в InstantCMS, могли участвовать в конструкторе.

Это должно работать в двух смыслах:

1. Пользовательский тип контента как источник данных.
2. Пользовательский тип контента как целевая страница/шаблон.

### Как источник данных

Пользовательский тип контента должен участвовать в блоках конструктора через:

- списки материалов;
- карточки;
- категории;
- связанные материалы;
- выбор одного материала;
- динамические ленты.

### Как целевая страница

Если новый тип контента создан внутри стандартной content-системы InstantCMS, его нужно проектно считать совместимым с конструктором по умолчанию или через opt-in механизм.

Рекомендуемый вариант:

- дать для каждого ctype настройку `участвует в конструкторе`;
- отдельно включать режимы:
   - list page builder support;
   - item page builder support;
   - category page builder support.

Почему это реалистично:

- content types в InstantCMS рендерятся через общий механизм шаблонов списка и карточки;
- это делает их намного проще для интеграции, чем, например, профиль пользователя.

Результат этапа:

- opt-in модель для custom content types;
- список режимов участия ctype в конструкторе;
- единый контракт для dynamic blocks, который не зависит от конкретного ctype.

Критерий готовности:

- новый пользовательский тип контента можно подключить к конструктору без переписывания ядра.

### 🔵 В работе: роль MCP уже определена, но не встроена в процесс разработки
