# Продуктовый blueprint: visual-first builder Нордик

## Зачем этот документ

Этот документ фиксирует продуктовый UX Нордик после разворота в visual-first builder.

Он нужен, чтобы не возвращаться к ошибочному сценарию, где пользователь сначала ходит по отдельным формам настроек, а только потом пытается понять, как это влияет на страницу.

Главный принцип:

Пользователь должен менять страницу прямо на живом холсте, а не собирать результат через цепочку экранов настроек.

Этот blueprint описывает главный ежедневный экран в более широкой взрослой архитектуре Нордик.

Текущий `landingbuilder` в репозитории считается переходным bridge-слоем, но канонический продукт уже мыслится шире: как отдельный visual-builder слой над InstantCMS 2 с собственным runtime, design system, component library и adapter-уровнем.

## 1. Каноническая модель продукта

Нордик теперь состоит из шести слоев:

1. `InstantCMS 2 Backend Layer`;
2. `Nordic Template Runtime`;
3. `Design System / Global Defaults`;
4. `Visual Builder Workspace`;
5. `Component Library`;
6. `Widget/Data Adapter Layer`.

### 1.1. Роль каждого слоя

#### `InstantCMS 2 Backend Layer`

Отвечает за:

1. routing;
2. users и permissions;
3. content types и categories;
4. system widgets;
5. SEO и системные страницы.

Это не builder-экран, а backend-фундамент продукта.

#### `Nordic Template Runtime`

Отвечает за:

1. публичный shell сайта;
2. header/footer и slot-зоны;
3. runtime rendering страницы;
4. применение design tokens на frontend;
5. связь shell и page output.

`Shell Builder` является expert-screen над этим runtime-слоем, а не главным ежедневным интерфейсом пользователя.

#### `Design System / Global Defaults`

Отвечает за:

1. site-wide tokens и presets;
2. палитру, типографику, spacing и surfaces;
3. дефолтные buttons, cards и shell surfaces.

Это вторичный экран defaults, а не место повседневной работы со страницей.

#### `Visual Builder Workspace`

Отвечает за:

1. порядок секций;
2. page-like preview;
3. выбор страницы, секции, колонки и элемента кликом по canvas;
4. device preview;
5. прямую визуальную сборку страницы.

Это главный продуктовый экран.

#### `Component Library`

Отвечает за:

1. готовые section presets;
2. block presets;
3. page templates и reusable patterns;
4. контролируемый набор builder primitives.

Именно этот слой не дает продукту скатиться в raw grid editor.

#### `Widget/Data Adapter Layer`

Отвечает за:

1. системные widgets InstantCMS как canvas nodes;
2. data-driven blocks;
3. единый runtime/data contract для preview и frontend.

Он не должен диктовать технический UX пользователю.

### 1.2. Каноническая модель сборки

Внутри visual builder продукт теперь считается не freeform canvas builder, а guided builder.

Каноническая иерархия такая:

1. `Страница`;
2. `Секции`;
3. `Блоки`;
4. `Элементы`.

То есть пользователь не собирает страницу из raw rows, cols и CSS-классов.

Он выбирает контролируемые визуальные сущности, а runtime и design system уже дают им структуру, ритм и default styling.

## 2. Как должен выглядеть главный экран

### 2.1. Общая композиция

Главный экран должен иметь 4 зоны:

1. верхняя панель действий;
2. левая библиотека;
3. центральный live canvas;
4. правая context sidebar.

Схема экрана:

`Top bar -> Left library -> Live canvas -> Right inspector`

Обязательные продуктовые правила:

1. левая и правая панели на desktop работают как overlay drawers поверх workspace;
2. canvas живет в отдельном wide viewport-слое;
3. переключение device mode меняет preview viewport, а не только активную кнопку;
4. открытые панели не должны ломать ощущение цельной страницы в центре.

### 2.2. Верхняя панель

Верхняя панель должна содержать только понятные продуктовые действия:

1. название страницы;
2. статус страницы;
3. `Сохранить`;
4. `Предпросмотр`;
5. `Опубликовать`;
6. `Компьютер`, `Планшет`, `Телефон`;
7. undo/redo;
8. переход к редким глобальным стилям.

Верхняя панель не должна показывать:

1. layout rows;
2. layout cols;
3. shell slot ids;
4. raw breakpoint names;
5. служебные позиции и внутренние ключи схемы.

### 2.3. Левая библиотека

Левая панель остается библиотекой визуальных сущностей, а не деревом технических узлов.

Для MVP остаются 4 вкладки:

1. `Секции`;
2. `Блоки`;
3. `Системные виджеты`;
4. `Шаблоны`.

Пользователь должен добавлять готовые визуальные секции и блоки, а не пустые строки и колонки.

### 2.4. Центральный canvas

Canvas должен выглядеть как реальная страница.

На canvas пользователь должен видеть:

1. реальные отступы;
2. реальные контейнеры и ширины;
3. реальную типографику;
4. фон секций;
5. вложенные блоки;
6. выделение выбранной области;
7. overlay controls без разрыва компоновки.

На canvas нельзя показывать:

1. названия HTML-тегов;
2. raw CSS-классы;
3. database ids;
4. служебные wrapper names;
5. bootstrap class names.

### 2.5. Правая sidebar

Sidebar всегда контекстная.

1. если ничего не выбрано, показываются настройки страницы;
2. если выбрана секция, показываются настройки секции;
3. если выбран блок, показываются настройки блока;
4. если выбран системный widget, показывается его сокращенный context-edit режим.

## 3. Какие controls оставляем в inspector

### 3.1. Page-level

Когда выбрана страница, в inspector оставить:

1. `Название страницы`;
2. `URL / slug`;
3. `SEO basics`;
4. `Шаблон страницы`;
5. `Стиль страницы`;
6. `Page style overrides`;
7. `Visibility / publish status`.

### 3.2. Section-level

Когда выбрана секция, в inspector оставить только продуктовые controls:

1. `Вариант секции`;
2. `Ширина контента`;
3. `Внутренние отступы`;
4. `Расстояние до следующей секции`;
5. `Фон секции`;
6. `Тон секции`;
7. `Style preset`;
8. `Layout preset`;
9. `Выравнивание контента`;
10. `Видимость на устройствах`;
11. `Дублировать`;
12. `Удалить`.

Чего не должно быть в section inspector:

1. выбора `div` / `section` / `article` для типового пользователя;
2. `container-fluid`;
3. `col-lg-*`;
4. ручного ввода CSS-классов;
5. wrapper HTML;
6. nested row positions.

### 3.3. Block-level

Когда выбран блок, в inspector оставить:

1. `Содержимое`;
2. `Размер`;
3. `Выравнивание`;
4. `Отступы`;
5. `Вариант оформления`;
6. `Видимость на устройствах`;
7. `Эффект`;
8. `Дублировать`;
9. `Удалить`.

### 3.4. System widget-level

Когда выбран системный widget, в inspector оставить:

1. `Название виджета`;
2. `Базовые options`;
3. `Видимость на устройствах`;
4. `Внешний отступ / container preset`;
5. `Переместить / дублировать / удалить`.

### 3.5. Responsive controls

Responsive controls остаются простыми:

1. `Компьютер`;
2. `Планшет`;
3. `Телефон`.

Для секций и блоков в этих режимах разрешены только понятные настройки:

1. показывать или скрывать;
2. менять layout preset;
3. менять порядок колонок;
4. менять вертикальные отступы;
5. менять gap между колонками.

## 4. Какие section presets даем в MVP

### 4.1. Базовый список

В первой версии достаточно 12 section presets:

1. `Hero simple`;
2. `Hero media left`;
3. `Hero media right`;
4. `Benefits 3 cards`;
5. `Features 2 columns`;
6. `Logo cloud`;
7. `Stats row`;
8. `Testimonials`;
9. `FAQ accordion`;
10. `CTA banner`;
11. `Contacts + map`;
12. `Rich text section`.

### 4.2. Layout presets

Для внутренней раскладки секций оставить контролируемые layout presets:

1. `1col`;
2. `2col_equal`;
3. `2col_media_text`;
4. `2col_text_media`;
5. `2col_sidebar_left`;
6. `2col_sidebar_right`;
7. `3col_equal`.

Пользователь должен выбирать визуальные карточки-layout presets, а не классы.

### 4.3. MVP structural actions

Для секций в MVP должны быть доступны только:

1. добавить секцию сверху или снизу;
2. перетащить секцию;
3. дублировать секцию;
4. удалить секцию;
5. сменить layout preset;
6. сменить style preset;
7. настроить visibility по устройствам.

Свободный конструктор сетки для первой версии не нужен.

## 5. Как связать builder с global defaults

### 5.1. Что такое global defaults

Global defaults это отдельный слой токенов и пресетов, который живет выше конкретной страницы, но не заменяет live editing на canvas.

Он задает:

1. brand colors;
2. page backgrounds;
3. heading scale;
4. body typography;
5. container widths;
6. section spacing scale;
7. buttons;
8. cards.

### 5.2. Как пользователь должен работать с ними

Канонический порядок действий теперь такой:

1. открыть страницу;
2. работать на canvas;
3. при необходимости открыть global defaults для site-wide базовых значений;
4. вернуться на canvas и сразу видеть тот же результат.

### 5.3. Порядок наследования стилей

Канонический порядок:

1. `core base tokens`;
2. `nordic base preset`;
3. `site global defaults`;
4. `page preset`;
5. `page overrides`;
6. `section overrides`.

Это должно работать через token merge, а не через ручные CSS-классы.

### 5.4. Что должен видеть пользователь вместо CSS

Вместо технических ключей пользователь должен видеть продуктовые названия:

1. `Широкий контейнер`;
2. `Стандартный контейнер`;
3. `Узкий текстовый контейнер`;
4. `Большой верхний отступ`;
5. `Средний зазор между секциями`;
6. `Основная кнопка`;
7. `Мягкая карточка`;
8. `Темная секция`;
9. `Акцентный фон`.

## 6. Что остается в widgets-схеме и shell

Widgets-схема и shell-слой остаются только для:

1. shell map preview;
2. системных widget zones;
3. продвинутой настройки shell;
4. диагностики bind positions.

Через них нельзя заставлять пользователя:

1. строить страницу из рядов;
2. задавать адаптивность руками;
3. выбирать HTML-теги;
4. вводить CSS-классы;
5. собирать content layout секций.

## 7. MVP сценарий пользователя

Правильный сценарий новичка выглядит так:

1. пользователь создает страницу;
2. открывает visual editor;
3. сразу видит живой canvas;
4. кликом выбирает нужную область;
5. меняет стиль справа и сразу видит ответ на холсте;
6. добавляет секции и блоки из левой панели;
7. переключает `Компьютер / Планшет / Телефон`;
8. заполняет контент;
9. при необходимости корректирует global defaults;
10. нажимает `Предпросмотр` и `Опубликовать`.

На этом пути он не должен упираться в технические поля и low-level layout vocabulary.

## 8. Что считаем зафиксированным продуктовым решением

1. Основной UX Нордик строится вокруг живого canvas, а не вокруг отдельного экрана настроек.
2. Live Inspector является главным инструментом стилизации.
3. Global defaults остаются отдельным экраном, но не являются primary flow.
4. Shell остается системным и expert-level слоем.
5. Sidebar редактирует presets и tokens, а не CSS-классы.
6. Responsive UX работает через режимы `Компьютер`, `Планшет`, `Телефон`.
7. Первая версия строится на контролируемых section presets, а не на freeform layout builder.

## 9. Канонический MVP-план на 3 этапа

### Этап 1. Foundation Layer

На первом этапе фиксируем фундамент взрослого продукта:

1. канонический JSON schema contract;
2. единый runtime contract для canvas, preview и live frontend;
3. design system token model;
4. базовую component library sections и blocks;
5. bridge-стратегию, где текущий `landingbuilder` переиспользуется как переходный runtime/editor полигон.

### Этап 2. Visual Editor Core

На втором этапе строим взрослый ежедневный интерфейс:

1. live inspector с понятными вкладками `Контент`, `Layout`, `Стиль`, `Дополнительно`;
2. page, section и block editing прямо на canvas;
3. responsive editing в режимах `Компьютер`, `Планшет`, `Телефон`;
4. устойчивый save/preview/publish loop без расхождения результата.

### Этап 3. System Integration Layer

На третьем этапе подключаем сильные стороны InstantCMS без поломки UX:

1. widget/data adapters;
2. shell participation visibility внутри canvas;
3. page templates и reusable component packs;
4. secondary screen `Глобальные стили` в финальной упрощенной роли.

Это и есть зафиксированный взрослый коридор MVP: сначала foundation, потом editor core, потом системная интеграция.
